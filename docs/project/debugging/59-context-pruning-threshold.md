# Bug: Context-Threshold Auto-Pruning Not Triggering

- **Status:** Resolved
- **Milestone:** N/A
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms
Expected: When the accumulated context token count exceeds the configured threshold (`turn_context_threshold`), the session pruning service should prune/prune-eligible turns so the working context stays bounded.
Actual: Sessions are observed to exceed ~150k context tokens with little session context present, and pruning does not appear to fire.
Reproduction steps: [TBD — to be established via MRE]

## Context & Scope
### Regressing Delta
The regression was introduced by commit `2b45601b` — `refactor(windows-startup-latency): make context re-gather fallback-only` (2026-10-01). It introduced the `project_context is None` gate in `SessionOrchestrator.execute` and relocated the sole `SessionPruningService.prune()` call into the new `_gather_fallback_context` helper ("fallback-only"). Before the refactor the re-gather (and its `prune()` call) ran on every session turn; after it, `prune()` runs ONLY when no context is provided — i.e., never on the primary interactive/pipeline path.
### Environmental Triggers
Any interactive or `-p` pipeline session turn (the primary path, where `SessionLifecycleManager._handle_planning_and_execution` forwards a planning-gathered `project_context`). No special OS or config is required; the bundled and live `.teddy/config.yaml` both set `turn_context_threshold: 50000`.
### Ruled Out
- Config resolution (key present in both baseline and user config; resolved to 50000) — NOT the cause.
- `token_count` being None/absent (it is a populated `int`) — NOT the cause.
- Scope-label mismatch (caller keys are exactly `"Turn"`/`"Session"`) — NOT the cause.
- Discarded `prune()` return value (consumed at session_orchestrator.py:449) — NOT the cause.
- `include_tokens=False` on the session path (only the standalone `context` command passes False) — NOT the cause.
- Downstream manifest propagation (`pruned_context` metadata → `discard` in `transition_to_next_turn`) — the mechanism is intact; it simply never receives any pruned paths.

## Diagnostic Analysis
### Causal Model
The pruning pipeline is `SessionPruningService.prune(context, current_status)`:
1. Bail if `auto_pruning.enabled` is falsy or context is not a dataclass.
2. Heuristics 3 & 4 (status/validation) → mark turns `selected=False`.
3. `_apply_retention_limit` (max_turns_retention=10) → deselect old turns.
4. `_apply_global_budget` → if `turn_context_threshold > 0`, sum `token_count` over items where `selected AND scope == "Turn"`; if sum > threshold, deselect largest Turn-scope items until under budget.
The budget heuristic keys EXACTLY on the literal scope string `"Turn"`. `ContextItem.scope` is assigned in `context_service._collect_items` from the KEYS of the `scoped_paths` dict passed to `get_context`. Therefore the scope literal produced by the caller determines whether the budget heuristic ever sees any tokens.
Confirmed inputs: `token_count` is a populated `int` (context_service.py:258); config key `auto_pruning.turn_context_threshold` = 50000 is present in both baseline and live `.teddy/config.yaml`. Caller scope keys are EXACTLY `"Turn"` and `"Session"` (session_cli_handlers.py:556-557; session_repository.py:192-193), and the `prune()` result IS consumed by turn assembly (session_orchestrator.py:449).
Dedup-upgrade subtlety: `_collect_items` (context_service.py:254) upgrades a path's scope from `"Turn"` to a non-Turn scope when the same path appears in both manifests — Session-wins. Any working-set file promoted to Session scope therefore ESCAPES the Turn-only budget sum.
Rendering subtlety: `ProjectContext.content_tokens` counts the ENTIRE rendered `content` (repo tree + git status + Resource Contents + Session History), whereas the budget sums ONLY selected `"Turn"` items. A large non-Turn payload (repo tree, Session History, system prompt) inflates the user-visible number without ever being prune-eligible.
Open: (i) whether the session-path `get_context` call passes `include_tokens` (default True); (ii) what session.context/turn.context actually reference in a live session and which scope the Session History files land in; (iii) whether the observed ~150k is dominated by non-Turn content (repo tree / session history / system prompt) rather than Turn-scope files.

Turn 04 refined the picture: there are TWO `get_context` call sites on the session path. (a) `PlanningService.generate_plan` (planning_service.py:74) builds its OWN unpruned context and sends `header+content` to the LLM as the user message. (b) `SessionOrchestrator._gather_context` (session_orchestrator.py:434) builds context AND runs `prune()`, returning the pruned context whose deselected `items` drive `_harvest_context` → `pruned_context` metadata → next-turn turn.context removal. Crucially `ProjectContext.content` (the payload actually sent to the LLM) is rendered from the UNPRUNED `scoped_paths` in `context_service._format_content`, so pruning has NO effect on the current turn's payload — it can only take effect on the NEXT turn via harvesting. If the harvest consumes the UNPRUNED context (from the planning path) instead of the pruned one, pruning never removes anything and the payload grows unbounded.
Also confirmed: `include_tokens=False` is passed ONLY by the standalone `context` command (session_cli_handlers.py:598); both the planning path and the orchestrator path leave it at the default True, so `token_count` IS populated on the session path.

Turn 06 confirmed the pruning→manifest propagation path: `SessionOrchestrator._harvest_context` (called at session_orchestrator.py:258) collects `[item.path for item in project_context.items if not item.selected]` into `plan.metadata["pruned_context"]`; `SessionLifecycleManager.finalize_turn` (session_lifecycle_manager.py:458-470) reads that metadata and passes `pruned_paths` to `SessionService.transition_to_next_turn`, which reads the CURRENT turn's `turn.context`, `discard`s each pruned path, re-applies execution effects, then adds the current turn's `plan.md` + `report.md` — OR routes them to `session.context` when the turn is a "preserved" (message/user-request) turn — and writes the NEXT turn's `turn.context`. On-disk evidence: `turn.context` accumulates per-turn plan.md/report.md (Turn scope); `session.context` holds init/README/PROJECT/ARCHITECTURE/initial_request (Session scope, budget-EXEMPT).
Turn 07 (DECISIVE): `SessionOrchestrator.execute` prepares context as:
```
if is_session and plan_path and project_context is None:
    project_context = self._gather_fallback_context(plan, plan_path)
self._harvest_context(is_session=is_session, project_context=project_context, plan=plan)
```
The ONLY call to `self._pruning_service.prune(...)` (line 449) lives INSIDE `_gather_fallback_context` (line 399), whose docstring states it is the "Fallback-only path: NEVER hit when `project_context` is provided (the Wiring threads the planning-gathered context through the lifecycle funnel)." Therefore, on the PRIMARY session path (a context IS provided), `prune()` NEVER runs; `_harvest_context` receives an UNPRUNED context whose items are all `selected=True`, so `pruned_paths` is empty and `plan.metadata["pruned_context"]` is never set. The downstream `transition_to_next_turn` `discard` (the only manifest-level pruning) therefore removes nothing, and `turn.context` grows unbounded — matching the symptom exactly.
Turn 08 CONFIRMED the regressing delta: commit `2b45601b refactor(windows-startup-latency): make context re-gather fallback-only` introduced BOTH the `project_context is None` gate and the `_gather_fallback_context` method (verified via `git log -S` on the gate string and the method name — both resolve to this single commit). A census of `planning_service.py` found ZERO prune references, so the planning LLM payload is always built from an UNPRUNED context. The lifecycle funnel forwards `project_context=` into `_handle_planning_and_execution` (session_lifecycle_manager.py:110/125/237), consistent with the `_gather_fallback_context` docstring claim that the wiring threads a planning-gathered context into `execute`. Because the retention limit (`_apply_retention_limit`) ALSO lives inside `prune()`, this single bypass disables ALL pruning heuristics, not just the budget.
Turn 09 CONFIRMED the final plumbing: `_handle_planning_and_execution` calls `trigger_new_plan(...)` (which returns `gathered_context`) and forwards it via `orchestrator.execute(..., project_context=(gathered_context if gathered_context is not None else project_context))`. On every normal session turn a non-None context reaches `execute`, so the `project_context is None` gate is False, `_gather_fallback_context` (and its sole `prune()` call) is skipped, `_harvest_context` sees an all-`selected=True` context, `pruned_context` is never populated, and `transition_to_next_turn` discards nothing — `turn.context` grows unbounded. Because `_apply_retention_limit` also lives inside `prune()`, retention is bypassed too.
VERIFIED FIX (Shadow File, Turns 11-12): hoisting the `prune()` call OUT of `_gather_fallback_context` and INTO `execute` (running on whichever context is present, BEFORE `_harvest_context`) flips the MRE from FAIL to PASS — primary-path `prune() calls` 0→1 and `pruned_context` None→'big1.py', while the fallback path remains 1 (no double-prune).
CATEGORY (Systemic Audit, Turn 15): this is an instance of "a MANDATORY side-effect captured inside a performance-gated / fallback-only branch", so the side-effect silently stops running on the primary path. The refactor slice `00-20` and its `orchestrator_execute_audit.md` confirm the "fallback-only" intent targeted the `re-gather` (an optional acquisition) but the `prune` side-effect was swept in with it. A categorical `git grep` census of `src/` found NO sibling mandatory-side-effect captures behind `fallback`/`is None` gates — every other `fallback` hit is a legitimate value/format fallback (adapters, parser matchers) with no mandatory side-effect. Impact Audit: `prune()` has exactly ONE production call site and `execute()` is invoked only from the lifecycle funnel / composition root (`__main__`, `cli_helpers`, session loop) → the fix is a single-file, internal change with no Port/DTO/Signature impact (no Vertical Slice required).

## Solution

### Root Cause
`SessionPruningService.prune()` is the single entry point for ALL auto-pruning heuristics (global token budget, turn retention limit, failure-history cleanup, validation-failure cleanup). Commit `2b45601b` — `refactor(windows-startup-latency): make context re-gather fallback-only` (2026-10-01) — introduced a `project_context is None` gate in `SessionOrchestrator.execute()` and relocated the sole `prune()` call into the new `_gather_fallback_context()` helper, whose own docstring declares it the "Fallback-only path: NEVER hit when `project_context` is provided". On every normal session turn (interactive or `-p` pipeline), `SessionLifecycleManager._handle_planning_and_execution` gathers context during planning and forwards it into `execute(project_context=...)`. Because that context is non-None, the fallback is skipped and `prune()` never runs. `_harvest_context()` then receives an all-`selected=True` context, `plan.metadata["pruned_context"]` is never populated, and `SessionService.transition_to_next_turn` discards nothing — so `turn.context` accumulates every prior turn's `plan.md`/`report.md` without bound. Because `_apply_retention_limit` (the `max_turns_retention` heuristic) also runs inside `prune()`, retention is bypassed too. This precisely explains the symptom: sessions exceed ~150k tokens while `session.context` stays tiny — the bloat is the per-turn working set in `turn.context`, exactly what the Turn-scope budget and retention heuristics are meant to bound.

### Proven Fix
Hoist the `prune()` call OUT of `_gather_fallback_context()` and INTO `execute()`, running on whichever context is present (primary OR fallback), immediately BEFORE `_harvest_context()`; remove the now-duplicate block from `_gather_fallback_context()` to avoid double-pruning. Proven by the Shadow File methodology (zero edits to `src/`): the primary-path `prune()` call count flips 0→1 and `pruned_context` goes `None`→`'big1.py'`, while the fallback path stays at 1 (no double-prune).

### Preventative Measures (Systemic)
This is an instance of a recurring class: **a mandatory side-effect captured inside a performance-gated/fallback-only branch**, so the side-effect silently stops running on the primary path. Preventatives:
1. **Primary-path regression test (Poka-Yoke):** add a pruning test that calls `execute(..., project_context=<oversized>)` and asserts pruning fires — closing the coverage gap (all 8 existing pruning tests only exercised the fallback path, which is why this regression shipped undetected).
2. **Document the invariant:** state in the `session_orchestrator` component doc that `prune()` MUST run on every session turn regardless of which path produced the context.
3. **Gating discipline:** when gating a step for performance, keep side-effects (pruning, harvesting, persistence) on the always-run path — the gate may make *acquisition* optional but never the *consumption/side-effect*.
