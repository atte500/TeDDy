# Bug: Execute-Mode READ Duplicates Content in Report

- **Status:** Resolved
- **Milestone:** N/A
- **Vertical Slice:** N/A
- **Specs:** [report-format.md](/docs/project/specs/report-format.md)

## Symptoms

- **Expected:** In `teddy execute` mode (non-session), a plan containing a `READ` action scoped to specific lines renders the READ contents exactly once in the generated report.
- **Actual:** The READ contents appear twice in the report.
- **Minimal Reproduction Steps:**
  1. Run `teddy execute` (non-session mode) with a plan containing a `READ` action with line-range parameters targeting an existing file.
  2. Inspect the produced report: the same file content appears in two places.

## Context & Scope

### Regressing Delta

- **`bdaf6ab7`** (Revert "feat(history-log): implement Tee utility class for stdout tee'ing", Jun 9): restored the inline `params.get('lines')` render block in the Action Log (verified via `git show bdaf6ab7 -- .../execution_report.md.j2`). This is the commit that introduced the second render path for line-scoped READ content.
- **`47ac725c`** ("fix(template): suppress Resource Contents note for line-range READ actions", Jun 10): changed only the Action Log note condition (`{% if action_type == 'READ' %}` → `{% if action_type == 'READ' and not params.get('lines') %}`), acknowledging the inline path for line-scoped reads but WITHOUT updating the `content_logs` collector to exclude those logs.
- The `content_logs` collector itself predates both (`ed161f6d`, slice 33 report generation enhancements) and was never amended.
- Net delta: the two render paths coexist with contradictory complementarity assumptions; any successful line-scoped READ in non-session mode duplicates content since `bdaf6ab7`.
- Workspace state: HEAD is 3 commits behind `origin/main`; probed via `git log HEAD..origin/main --name-only` — none of the upstream commits touch the report template or pipeline, so the locally-verified delta analysis remains valid.

### Environmental Triggers

- Non-session `teddy execute` mode (reported trigger; session-mode contrast VERIFIED via MRE: session mode renders the content exactly once because the `content_logs` collector path is suppressed by `is_session`).
- `READ` action with specific lines (line-range parameters).

### Ruled Out

- `action_executor.py`: READ logs pass through untouched — `_enrich_failed_log` only enriches FAILED CREATE/EDIT logs with file content; successful READ content capture is unaffected.
- `execution_report_assembler.py`: performs a straight DTO copy (`action_logs` passed as-is into `ExecutionReport`); no duplication possible.
- `markdown_report_formatter.py` (Python layer): only prepares context (`is_session`, `format_datetime`) and post-processes whitespace; no READ-content branching.
- Proven by MRE construction: the MRE renders a single `ActionLog` directly through the formatter, bypassing executor/assembler/io entirely, and still reproduces the duplication — isolating the defect to `execution_report.md.j2`.

## Diagnostic Analysis

### Causal Model

Verified statically (full read of `execution_report.md.j2`, Turn 1): READ content travels in `ActionLog.details['content']`. The template builds a `content_logs` namespace collecting every log whose `details` is a mapping containing `content` and whose status is FAILURE, or whose action is a SUCCESSFUL READ — with NO exclusion for line-scoped reads. When `is_session` is False, all collected logs render under `## Resource Contents` (render path 1). Independently, inside the `## Action Log` loop, a second block renders `log.details.content` fenced whenever the action is a READ and `params.get('lines')` is truthy — with no `is_session` guard (render path 2). The note logic ("Up-to-date contents are provided under `Resource Contents`", shown only when `lines` is NOT set) proves the paths were designed to be complementary (inline INSTEAD of Resource Contents for line-scoped reads), but the collector was never updated to exclude line-scoped READs. Net effect: successful line-scoped READ + non-session mode → both paths fire → content rendered twice. Session mode suppresses path 1 → single inline render. The duplication is a rendering-layer gating defect in the template collector, not an executor/assembler defect. Dynamic confirmation: the MRE reproduced the symptom (execute mode: 2 sentinel occurrences; session mode: 1), and by constructing the report DTO directly it isolates the defect to the template layer. Regressing delta attribution: `bdaf6ab7` (revert of history-log Tee) added the inline `params.get('lines')` render block; `47ac725c` added the complementary note suppression but left the collector unexcluded. Fix proven via Zero-Touch Verification: a shadow template replica whose collector excludes successful line-scoped READs renders 1 sentinel occurrence in BOTH modes (exit 0), confirming the collector exclusion as the sufficient and minimal fix. Systemic Audit finalized the fix in DRY form: a single classification pass (`resource_logs`/`inline_logs`) is now the one source of truth for content render placement, with all downstream sites consulting membership — verified equivalent via MRE (1 sentinel in both modes, exit 0). The audit confirmed no second live dual-render instance (`failed_resources` and the collector cover disjoint execution paths).

### Discrepancies

A successful line-scoped READ in non-session mode fires both, rendering the content twice; session mode suppresses the collector path, leaving the inline render once — consistent with the execute-mode-only report.)

## Solution

**Root cause:** The report template encoded the "where does READ content render?" policy in two independent conditionals — the `content_logs` collector (gated on `not is_session`, with no exclusion for line-scoped READs) and the inline Action Log block (gated on a truthy `lines` param, with no session guard). The inline block entered via `bdaf6ab7` (revert of the history-log Tee feature) against a collector that predates it (`ed161f6d`, slice 33); `47ac725c` acknowledged the intended complementarity in the note logic ("Up-to-date contents are provided under `Resource Contents`" shown only when `lines` is NOT set) but never reconciled the collector. Any successful line-scoped READ in non-session mode therefore fired both paths, rendering its content twice (once under `## Resource Contents`, once inline). Session mode suppresses the collector path, which is why the symptom was execute-mode-only.

**Proven fix:** Classify each content-bearing log exactly once in a single template pass into `resource_logs` (rendered under `## Resource Contents`, non-session only) or `inline_logs` (rendered fenced inline in the Action Log), and have all downstream render sites (Resource Contents section, note bullet, inline block) consult list membership instead of re-deriving the gating conditions. Verified via Zero-Touch Verification: the DRY shadow template renders the MRE sentinel exactly once in BOTH modes (exit 0). Behavioral contract restored: full READs → Resource Contents; line-scoped READs → inline only; failures → Resource Contents regardless; session mode → inline only.

**Systemic preventative measures (bug class: divergent duplicate gating logic):**
- The DRY classification pass is the single source of truth for render placement — the policy can no longer drift apart across independently-edited conditionals, which was the root cause mechanism.
- A dedicated regression test (Phase 6) asserts a successful line-scoped READ renders exactly once in both modes, anchoring the complementarity contract in the test suite. The pre-existing acceptance test `test_execute_read_adhoc_params.py::test_read_lines_range` — whose documented intent is line-range extraction, with the Resource Contents lookup as its former extraction vehicle — was aligned to the approved placement: it now asserts the content renders exactly once inline and is absent from Resource Contents.
- Residual structural risk harvested as `[DEBT]`: the template retains two separate `## Resource Contents` render sites (`report.failed_resources` for validation-failure reports vs the classified `resource_logs` for execution reports). The Systemic Audit verified they currently cover disjoint execution paths (validation-failure reports carry no enriched action logs; execution reports do not populate `failed_resources`; session mode suppresses both), so no live duplication exists — but a future change bridging the paths could re-introduce this bug class; consolidation into the single classification pass is logged for Milestone 5.
