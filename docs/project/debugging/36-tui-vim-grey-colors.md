# Bug: TUI Editor Shows Grey Colors (Vim Syntax Highlighting Not Applied)
- **Status:** Resolved
- **Milestone:** [Milestone 4: TUI & UX Enhancements](/docs/project/milestones/04-tui-ux-enhancements.md)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms

Pressing `e` on an EDIT action in the TUI plan reviewer opens a `.diff` file in vim, but all text appears in grey — no color highlighting for `---` (should be red) or `+++` (should be green) lines, even though the terminal reports 256 color support.

**Expected behavior:** Vim should correctly apply diff syntax highlighting with red for `---` lines, green for `+++` lines, and blue for `@@` hunk headers, matching the terminal's color capabilities.

**Actual behavior:** All text rendered in a single grey color, identical to plain text without syntax highlighting.

**Minimal reproduction:**
1. Start a TeDDy session with the TUI (`teddy start`)
2. Navigate to an EDIT action node in the action tree
3. Press `e` to open the annotated diff file
4. Observe: vim opens a `.diff` file but shows everything in grey

## Context & Scope

### Regressing Delta
The editor subsystem was overhauled in slices 00-16 and 00-17 to replace the vimdiff two-file flow with a single annotated `.diff` file. The implementation:
- Uses `difflib.unified_diff()` to generate the diff content
- Writes to a `.diff` file (for vim syntax detection)
- Launches with `subprocess.run()` inside `app.suspend()` (CLI editors)
- Added explicit `stdin=sys.stdin, stdout=sys.stdout, stderr=sys.stderr` forwarding (Turn 14)
- Previously had a `# vim: syntax=diff` modeline that was removed (Turn 14 per user request)

The colour issue was present before and after the modeline removal, confirming the modeline was not the fix.

### Environmental Triggers
- Observed with terminal editors (vim, nvim) in the TUI suspend context
- Terminal reports `TERM=xterm-256color`, `tput colors=256`
- Also tested outside TUI: vim correctly shows t_Co=256 and colors work when `subprocess.run()` is called directly without the suspend context
- macOS and Linux systems (TTY-based)
- Not reproducible outside the TUI (suspend/resume context appears to be the trigger)

### Ruled Out
- Missing explicit stdio forwarding (was added in Turn 14 — no effect)
- Vim modeline (`# vim: syntax=diff`) — removed in Turn 14, issue persisted
- `_restore_foreground_process_group()` — both paths call it
- `_restore_terminal_cooked_mode()` — both paths call it
- `_flush_stdin()` — both paths call it
- The `.diff` file extension — confirmed to trigger vim diff syntax when opened outside TUI

## Diagnostic Analysis

### Causal Model
The annotated diff is generated by `_generate_annotated_diff_content()` in `textual_plan_reviewer_editor.py` and written to a `.diff` temp file. The editor is launched inside `app.suspend()` using `subprocess.run()`.

**Suspend chain (Textual 8.2.8):**
1. `App.suspend()` → `self._driver.suspend_application_mode()` → calls `self.stop_application_mode()` (abstract) then `self.close()` (stops writer thread)
2. Yields inside `redirect_stdout(sys.__stdout__)`, `redirect_stderr(sys.__stderr__)` context
3. On exit: `self._driver.resume_application_mode()` → `self.start_application_mode()` (abstract)

**LinuxDriver behavior:**
- `start_application_mode()` saves terminal attrs: `self.attrs_before = termios.tcgetattr(self.fileno)`
- `stop_application_mode()` (inherited abstract) calls terminal restore via `termios.tcsetattr(self.fileno, termios.TCSANOW, self.attrs_before)`
- No override of `suspend_application_mode` or `resume_application_mode` — uses base `Driver` implementation which calls `stop_application_mode()` + `close()` / `start_application_mode()`

**Terminal state theory vs source:**
- Source shows terminal SHOULD be restored to pre-Textual state (cooked mode) before yielding
- The writer thread is stopped, so no escape sequences leak
- No evidence of terminal state corruption in the source

**Key diagnostic findings (MRE run, 2026-08-30):**
- **Confirmed:** Inside `app.suspend()`, vim with `-u NONE` reports `t_Co=256`, `term=xterm-256color`, `syntax_on=0`, `filetype=""`, `colors_name=NOT SET`.
- **Confirmed:** Diff highlight groups (DiffAdd/DiffDelete) have color definitions (`ctermbg=81`, `ctermfg=12`, etc.) — the color infrastructure is present but syntax engine is not active.
- **Hypothesis:** The grey colors are caused by `syntax_on=0` — vim's syntax highlighting engine is not activating, so no highlight groups are applied to specific tokens. Everything renders in the default foreground color (grey).
- **Remaining question:** When vimrc is loaded (real conditions, without `-u NONE`), does `syntax_on` become 1? If yes, the issue shifts to colorscheme or terminal capability. If no, something in the suspend context prevents vim from enabling syntax.

**Pending investigation:** Second MRE (`spikes/debug/36-mre-user-vimrc.sh`) runs the same diagnostic WITHOUT `-u NONE` to check if the user's vimrc correctly enables syntax inside the suspend context. User needs to run this script.

## Solution

### Root Cause
The user's vimrc did not contain `syntax on` or `syntax enable`. Vim requires an explicit directive to enable its syntax highlighting engine. Without it, `syntax_on` remains `0` and no highlight groups are applied to any tokens, causing all text to render in the terminal's default foreground color (grey).

Diagnostic MREs run inside `app.suspend()` confirmed:
- `t_Co=256`, `term=xterm-256color` — color capabilities are correct
- `syntax_on=0`, `filetype=""`, `colors_name=NOT SET` — the syntax engine is inactive
- Diff highlight groups (DiffAdd, DiffDelete, etc.) have color definitions but are never applied because `syntax_on=0`

### Fix
Added explicit `-c 'syntax on' -c 'filetype plugin on'` flags to vim/nvim commands in two places:

1. **`launch_editor()`** — when the resolved editor is a vim variant, the flags are appended before the file path.
2. **`preview_edit_diff_viewer()`** — when the diff viewer is a vim variant, the flags are appended to the single-file annotated diff command.

A new helper `_is_vim_editor()` detects vim/vi/nvim by checking the basename of the editor command (case-insensitive). This ensures the flags are only added for vim-based editors; other CLI editors (nano, micro, helix) are unaffected.

### Preventative Measures
This fix addresses the entire class of "vim user without `syntax on` in vimrc" issues. By injecting the flags at the TeDDy level, syntax highlighting works reliably regardless of the user's personal vim configuration. No systemic audit was required since this is a targeted vim-specific fix.
