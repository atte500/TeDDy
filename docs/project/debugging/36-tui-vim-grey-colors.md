# Bug: TUI Editor Shows Grey Colors (Vim Syntax Highlighting Not Applied)
- **Status:** Unresolved
- **Milestone:** [Milestone 4: TUI & UX Enhancements](/docs/project/milestones/04-tui-ux-enhancements.md)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms

Pressing `e` on an EDIT action in the TUI plan reviewer opens a `.diff` file in vim, but all text appears in grey — no color highlighting for `---` (should be red) or `+++` (should be green) lines, even though the terminal reports 256 color support.

**Expected behavior:** Vim should correctly apply diff syntax highlighting with red for `---` lines, green for `+++` lines, and blue for `@@` hunk headers, matching the terminal's color capabilities.

**Actual behavior:** All text rendered in a single grey color, identical to plain text without syntax highlighting.

**Minimal reproduction:**
1. Start a TeDDy session with the TUI (`teddy start`)
2. Navigate to an EDIT action node in the action tree
3. Press `e` to open the annotated diff file
4. Observe: vim opens a `.diff` file but shows everything in grey

## Context & Scope

### Regressing Delta
The editor subsystem was overhauled in slices 00-16 and 00-17 to replace the vimdiff two-file flow with a single annotated `.diff` file. The implementation:
- Uses `difflib.unified_diff()` to generate the diff content
- Writes to a `.diff` file (for vim syntax detection)
- Launches with `subprocess.run()` inside `app.suspend()` (CLI editors)
- Added explicit `stdin=sys.stdin, stdout=sys.stdout, stderr=sys.stderr` forwarding (Turn 14)
- Previously had a `# vim: syntax=diff` modeline that was removed (Turn 14 per user request)

The colour issue was present before and after the modeline removal, confirming the modeline was not the fix.

### Environmental Triggers
- Observed with terminal editors (vim, nvim) in the TUI suspend context
- Terminal reports `TERM=xterm-256color`, `tput colors=256`
- Also tested outside TUI: vim correctly shows t_Co=256 and colors work when `subprocess.run()` is called directly without the suspend context
- macOS and Linux systems (TTY-based)
- Not reproducible outside the TUI (suspend/resume context appears to be the trigger)

### Ruled Out
- Missing explicit stdio forwarding (was added in Turn 14 — no effect)
- Vim modeline (`# vim: syntax=diff`) — removed in Turn 14, issue persisted
- `_restore_foreground_process_group()` — both paths call it
- `_restore_terminal_cooked_mode()` — both paths call it
- `_flush_stdin()` — both paths call it
- The `.diff` file extension — confirmed to trigger vim diff syntax when opened outside TUI

## Diagnostic Analysis

### Causal Model
The annotated diff is generated by `_generate_annotated_diff_content()` in `textual_plan_reviewer_editor.py` and written to a `.diff` temp file. The editor is launched inside `app.suspend()` using `subprocess.run()`. The suspend/resume context manager in Textual performs TTY state modifications (switching to raw mode, disabling echo, etc.) on entry and restores on exit. Inside the suspend block, the child process (vim) inherits the current terminal state, which may have altered color capability flags or environment variables.

Key evidence from the terminal color capability probe:
- `isatty(0)=False` for all FDs inside subprocess (expected — child gets pipes, not TTY)
- `tput colors=256` still reports correctly
- ANSI escape sequences (`\033[31mRED`) work in captured output
- `vim -c 'echo &t_Co'` reports **256** even with `capture_output=True`
- Despite vim knowing about 256 colors, syntax highlighting does not render in the TUI suspend context

This suggests the issue is not vim's ability to detect colors, but rather that vim's **syntax highlighting engine** either:
1. Is not being activated for the `.diff` filetype inside the suspend context
2. Is being overridden by a colorscheme that uses grey for everything
3. The terminal state (raw mode from Textual) is preventing vim from properly initializing its highlighting

### Discrepancies
- Vim reports `t_Co=256` even inside the suspend context (proven by standalone `subprocess.run` test). Yet the visual output is grey. This contradicts the assumption that color detection alone determines highlighting.
- The `# vim: syntax=diff` modeline *should* force diff highlighting, but even when it was present (before removal in Turn 14), the colors were still grey. This suggests vim's ability to parse the modeline or apply the syntax file is compromised inside the suspend context.

### Investigation History
1. **Turn 7-14 (2026-08-30):** Added `# vim: syntax=diff` modeline as first line. User tested and confirmed "still all grey". Removed modeline per user request. Added explicit `stdin=sys.stdin, stdout=sys.stdout, stderr=sys.stderr` to all `subprocess.run()` calls. No improvement.
2. **Turn 20 (2026-08-30):** Created color capability probe (`spikes/color_capability_probe.py`). Ran inside current terminal (not TUI). Results: isatty=False for all child FDs, but `tput colors=256` works, ANSI codes output correctly. Key finding: The subprocess itself preserves color capability — the issue is specific to the TUI suspend context.
3. **Turn 20 (2026-08-30):** Ran direct vim color test (`vim -c 'echo &t_Co'`). Results: vim reports `t_Co=256` even when stdin/stdout is a pipe (not a TTY). Confirmed vim knows about 256 colors.
4. **Further investigation needed:** No testing has been done inside the actual TUI suspend context to check vim's `t_Co`, `colorscheme`, or `filetype` detection during suspension. A targeted TUI test is needed where `vim -c 'set verbose=9'` is used to diagnose why syntax highlighting fails.

## Solution
*No solution identified yet. Requires further investigation inside the TUI suspend context: check vim's `t_Co`, `filetype`, and `syntax on` status during suspension. Potential fixes:*
- *Set `FORCE_COLOR=1` before launching vim inside suspend*
- *Use `vim -c 'syntax on' -c 'colorscheme default'` to force highlighting*
- *Investigate if Textual's raw mode terminal state affects vim's color initialization*
