# Bug: Quit-Key Interrupt Latency After the Cross-Platform SIGINT Fix
- **Status:** Resolved
- **Milestone:** N/A (ad-hoc regression)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms
Pressing `q` during a session used to interrupt instantly. The notice `Interrupted by user (q).` appeared immediately, and the application exited. Since the cross-platform SIGINT fix, the notice appears only after about one second.
Reproduction: start an interactive session, send a message so a turn is in flight, press `q`, and observe the delay before the notice.

## Context & Scope
### Regressing Delta
- `fc5a44a9` added the shared `raise_interrupt` helper, which calls `signal.raise_signal(signal.SIGINT)`, in `src/teddy_executor/core/utils/interrupt_guard.py`.
- `c2c54063` routed the quit-key listener's self-delivery through `raise_interrupt` in `src/teddy_executor/adapters/outbound/terminal_quit_key_listener.py` (`_trigger`).
- Production path: `src/teddy_executor/container.py` (`_record_quit_source`) runs on the quit-key reader thread. It records `"q"` on the shared guard, then calls `raise_interrupt()`.

### Environmental Triggers
macOS (Darwin) with an interactive TTY session. The quit-key reader thread delivers the signal while the main thread blocks in a C-level wait, such as an LLM socket read or a subprocess wait.

### Ruled Out
- The quit-key reader poll interval (`_POLL_INTERVAL = 0.05` seconds) cannot explain a one-second delay.
- The stdin-ownership backoff is process-global and active only while a prompt owns stdin, not during planning or action execution.
- Cancelling the main thread's pending socket read with `CancelSynchronousIo` before raising. The probe recorded `[WinError 1168] Element not found.` on every wait shape and delivery still took 811 ms against the socket read, so the blocking Winsock call exposes no cancellable I/O to that API.

## Diagnostic Analysis
### Causal Model
The quit-key reader thread calls `signal.raise_signal(signal.SIGINT)`. On POSIX, that call delivers the signal to the calling thread through C `raise()`. Python records the signal and schedules the Python-level handler as a pending call on the main thread. The main thread runs the handler only when it returns from its current blocking call. The previous `os.kill(os.getpid(), signal.SIGINT)` delivered a process-directed signal that interrupted the main thread's blocking call. The observed latency therefore equals the remaining duration of that blocking call.
The MRE measured this mechanism directly. `raise_signal` from a worker thread reported 0.8 seconds of latency against a 1.0-second `select` wait and 2.8 seconds against a 3.0-second sleep. `os.kill` to the process, `pthread_kill` to the main thread, and the sandbox replica each reported 0.0 seconds. Delivery therefore wakes the handler immediately only when the signal targets the main thread.

The cross-platform probe extended this model to Windows. The CRT raise wakes alertable timer waits immediately: `raise_signal` reported 0 ms against `sleep_1s`, `sleep_3s`, a sliced `Future.result(timeout=1.0)`, and `Event.wait(1.0)`. The same call cannot wake a blocking socket read: it reported 803 ms against `socket_1s`, so the handler ran only when the read returned. Windows exposes no `pthread_kill` equivalent. Production blocks in a raw socket read during planning, because `PlanningService.generate_plan` calls `get_completion` directly on the main thread. Production blocks in 0.1-second sliced `communicate` waits during execution, because `ShellAdapter._await_process` checks the guard between slices. The Windows caveat is therefore confined to the planning wait.

A contained Windows wake-up was tested and refuted. `CancelSynchronousIo` against the main thread's handle returned `[WinError 1168] Element not found.` on every wait shape, and delivery still took 811 ms against the socket read, so the blocking Winsock call exposes no cancellable I/O to that API.

The probe then measured an unbounded `Future.result()` wait behind a safety release. Windows woke that wait at 0 ms through `raise_signal_current` and through the replica, and Linux woke it at 0 ms only through the main-thread targets while `raise_signal_current` needed 4800 ms. Running the blocking call on a daemon worker therefore keeps the main thread in a condition wait, which every delivery primitive already wakes. The composed MRE confirmed this end to end with a worker parked in a real socket read, a future wait on the main thread, and a third thread delivering the quit. The one-slice fix follows from that measurement. On POSIX the delivery helper targets the main thread, and on Windows the unchanged CRT raise wakes the future, so no Windows API and no poll interval are involved.

Planning also performs a second main-thread network read. `generate_plan` calls `get_context_window`, which reaches `OpenRouterMetadataHydrator._fetch_models`, which calls `requests.get(..., timeout=10.0)` on the calling thread whenever the persistent cache is missing or expired. A cold first turn therefore carries a hydration fetch beside the completion call, so the interruptible wrapper must span the hydration and token-count section as well as the completion call.

### Discrepancies
- [x] Pressing `q` no longer interrupts instantly. The notice is delayed by about one second. (Resolved: the reader thread delivers a thread-directed signal, so the handler waits for the main thread's blocking call to return; the MRE measured 0.8 seconds against a 1.0-second wait.)
- [x] The `raise_interrupt` docstring claims delivery reaches the handler from a reader thread on every platform. It does not reach the handler promptly while the main thread blocks. (Resolved: delivery reaches the handler only at the next main-thread bytecode checkpoint; the MRE measured 2.8 seconds against a 3.0-second block.)
- [x] Main-thread delivery was assumed to be fast on Windows in every wait shape. (Resolved: the CRT raise reported 0 ms against `time.sleep`, `Future.result`, and `Event.wait`, but 803 ms against a blocking socket read, and Windows exposes no `pthread_kill` equivalent.)
- [x] The production main thread was assumed to wait in a timer-like call that Windows can wake. (Resolved: `PlanningService.generate_plan` calls `get_completion` directly on the main thread, which performs a raw socket read, while `ShellAdapter._await_process` slices its `communicate` wait at 0.1 seconds, so the Windows caveat applies to planning only.)
- [x] A contained Windows wake-up was assumed to exist inside the delivery helper, through cancellation of the main thread's pending socket read. (Resolved: `CancelSynchronousIo` failed with `[WinError 1168] Element not found.` on every wait shape and delivery stayed at 811 ms against the socket read, so the fast path must stop blocking the main thread instead of cancelling its call.)
- [x] The Windows fast path was assumed to need a polled wait and therefore a separate scope. (Resolved: an unbounded `Future.result()` wait was woken at 0 ms by the CRT raise on Windows and at 0 ms by the main-thread target on Linux, so a worker plus future covers both platforms in one change and needs no poll interval.)
- [x] Planning was assumed to block only inside `get_completion`. (Resolved: `generate_plan` also calls `get_context_window`, which reaches `requests.get(..., timeout=10.0)` on the calling thread on a cache miss, so the interruptible wrapper must span the hydration and token-count section as well.)

## Solution
### Root Cause
`raise_interrupt` delivers SIGINT with `signal.raise_signal` from the quit-key reader thread. On POSIX that call is thread-directed, so the main-thread handler runs only at the next bytecode checkpoint, and the latency equals the remainder of the main thread's blocking call. The MRE measured 0.8 seconds against a 1.0-second wait and 2.8 seconds against a 3.0-second wait, while `os.kill` to the process and `pthread_kill` to the main thread both reported 0.0 seconds.
The proven fix targets the main thread on POSIX with `signal.pthread_kill(threading.main_thread().ident, signal.SIGINT)` and keeps `signal.raise_signal` on Windows and as fallback, so the Windows quit notice stays intact. The fix was proven in the sandbox replica at `spikes/debug/quit-key-interrupt-latency/replica_interrupt_guard.py` and was NOT applied to `src/`, because three test seams outside the helper's own unit suite stub `signal.raise_signal` and the change therefore exceeds the small-change scope. The Developer must implement it with the migrations below.
The cross-platform probe separated the two platform paths. On POSIX the replica fix reported 0 ms on every wait shape, including the raw socket read, so the reported regression disappears completely. On Windows the CRT raise reported 0 ms against `time.sleep`, `Future.result`, and `Event.wait`, but 803 ms against a raw socket read, and Windows exposes no `pthread_kill` equivalent. Production blocks in a raw socket read during planning, so the Windows quit notice can lag for the remainder of the LLM response. The proven fix therefore removes the POSIX regression and keeps the Windows notice intact, but it does not by itself make Windows fast during planning.
A contained Windows wake-up inside the delivery helper was tested and refuted in run `39579500381`. The measured alternative is simpler and covers both platforms in one change. An unbounded future wait is woken at 0 ms by the CRT raise on Windows and at 0 ms by the main-thread target on Linux (runs `39580764362` and `39581396641`), so running the planning network phase on a daemon worker while the main thread waits on its future removes the delay everywhere without a Windows API and without a poll interval.

The verified fix is therefore one vertical slice with two parts that compose. First, `raise_interrupt` targets the main thread on POSIX with `signal.pthread_kill` and keeps `signal.raise_signal` on Windows. Second, a small interruptible-call helper runs a blocking callable on a daemon worker and returns `future.result()` on the calling thread; `PlanningService.generate_plan` uses it around the hydration, token-count, and completion phase, so the main thread never sits in a raw socket read. Both parts were proven in the sandbox replicas at `spikes/debug/quit-key-interrupt-latency/replica_interrupt_guard.py` and `spikes/debug/quit-key-interrupt-latency/replica_interruptible_call.py`, and neither was applied to `src/`, because the change spans two production modules and several test modules and therefore exceeds the small-change scope. The Developer must implement it with the migrations below.

The trade-off is bounded and recorded. `get_completion` sends one non-streaming request, and the adapter exposes no cancellation handle, so the quit path cannot abort the in-flight call. The daemon flag guarantees the process exits immediately, and process exit kills the worker and closes its socket. The provider decides whether it aborts generation on that disconnect, and a non-streaming provider commonly finishes generating and bills the generated tokens. The adapter's 300-second default timeout bounds the worker whenever the process survives the quit.

### Affected Components
- `src/teddy_executor/core/utils/interrupt_guard.py` (`raise_interrupt`): replace the unconditional `raise_signal` with a main-thread `pthread_kill` on POSIX, keep the CRT raise path on Windows, and update the docstring so it no longer claims prompt reader-thread delivery. Do not add a Windows cancellation attempt here, because run `39579500381` refuted it.
- `src/teddy_executor/container.py` (`_record_quit_source`): consumer only, no signature change.
- `src/teddy_executor/adapters/outbound/terminal_quit_key_listener.py` (`_trigger`): consumer only, no signature change.
- `tests/suites/unit/core/utils/test_interrupt_guard.py`: the real-delivery test already drives the helper; add coverage that delivery reaches the handler while the main thread blocks.
- `tests/suites/integration/core/services/test_quit_source_wiring.py`: stubs `signal.raise_signal`, so it must stub the active POSIX primitive instead.
- `tests/suites/unit/adapters/outbound/test_terminal_quit_key_listener_reader.py`: two seams stub `signal.raise_signal`, so the self-delivery seam must observe the active POSIX primitive.
- `src/teddy_executor/core/utils/interruptible_call.py` (new module): add a small helper that runs a callable on a daemon worker and returns `future.result()` on the calling thread, forwarding both the result and every worker exception unchanged. The sandbox replica at `spikes/debug/quit-key-interrupt-latency/replica_interruptible_call.py` is the proven implementation.
- `src/teddy_executor/core/services/planning_service.py`: wrap the hydration, token-count, and completion phase in the new helper. The wrapper must span `get_context_window` as well as `get_completion`, because a cold or expired model-registry cache makes hydration perform its own `requests.get` on the main thread.
- `src/teddy_executor/adapters/outbound/litellm_adapter.py`: no change required. `get_completion` sends one non-streaming request and exposes no cancellation handle, so the quit path cannot abort it. The daemon worker dies with the process, and its socket closes at exit. Provider-side generation may continue and bill tokens after that disconnect, and the 300-second default timeout bounds a worker whose process survives. This is the documented trade-off.
- `tests/suites/unit/core/utils/test_interruptible_call.py` (new module): cover result forwarding, exception forwarding, and that the callable runs off the calling thread.
- `tests/suites/unit/core/services/test_planning_service.py`: cover that a quit during planning raises from the wait and leaves no blocking main-thread read.
- `spikes/debug/probe.sh`: tooling only. The `make probe` recipe ignores a failed artifact download, so a stale output file can look like fresh evidence. Read the step log with `make logs RUN=<run-id> STEP="Execute Remote Probe"` when the artifact is disputed.
