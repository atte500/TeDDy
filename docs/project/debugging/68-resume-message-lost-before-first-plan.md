# Bug: resume -m Message Not Durably Persisted (Pre-Plan & Mid-Session)
- **Status:** Resolved
- **Milestone:** N/A
- **Vertical Slice:** [00-21-session-interrupt-resume-message](/docs/project/slices/00-21-session-interrupt-resume-message.md)
- **Specs:** N/A

## Symptoms

**Expected behavior:**
- When a session is started (`teddy start`) and quit before the first plan is produced, a subsequent `teddy resume -m "<message>"` MUST append `<message>` to the session's `initial_request.md`, so the augmented request seeds the first plan.
- In ANY turn resumed with `-m`, the injected message MUST be recorded in `session.context` (not only `turn.context`) so it survives turn-scope pruning.

**Actual behavior:**
- **Pre-first-plan (`EMPTY`/turn `01`) — confirmed via MRE (Turn 7):** the `resume -m` message issued before the first plan is NOT appended to `initial_request.md` (the durable first-request artifact seeded into `session.context`). The augmentation is threaded only transiently into the imminent plan generation and is not persisted; a later bare `resume` falls back to the stale `initial_request.md`. The EMPTY-state resume path (`SessionLifecycleManager.resume`) attempts `_append_message_to_previous_turn`, but turn `01` has no predecessor (`00/report.md` never exists), so the call is a hard no-op.
- **Mid-session (`EMPTY`/turn `>01`) — confirmed via MRE (Turn 24):** `teddy resume -m "<message>"` on a completed turn `N` (whose empty successor `N+1` is the latest turn) DOES append the smart-fenced `## User Request` to turn `N`'s `report.md` via `_append_message_to_previous_turn`, but does NOT re-evaluate turn `N`'s preservation into `session.context`. Turn `N`'s preservation decision already ran during its OWN finalize (when it created turn `N+1`), BEFORE this append — so the augmented turn is never admitted to the prune-exempt session scope. The request therefore lands in `report.md` but remains subject to turn-scope pruning. (By contrast, the TUI `m` path renders the request into `report.md` BEFORE finalization, so that path IS preserved into `session.context` — matching the user's observation.)

**Minimal reproduction steps:**
1. `teddy start` (fresh session) and quit (Ctrl+C / `q`) before the first plan is produced.
2. `teddy resume -m "additional instructions"`.
3. Observe the message is lost: no append to `initial_request.md`, and the message is absent from `session.context`.
4. (Mid-session) Complete turn `N` of a session so its empty successor `N+1` is the latest turn; then `teddy resume -m "additional instructions"`. Observe the `## User Request` is appended to turn `N`'s `report.md`, yet turn `N`'s `plan.md`/`report.md` never appear in `session.context`.

## Context & Scope
### Regressing Delta
Not a code regression but an unhandled case introduced by slice `00-21-session-interrupt-resume-message`: the slice added `resume -m` threading and implemented persistence only for the `COMPLETE_TURN` (report append) and pipeline `AWAITING_REPLY` paths. The `EMPTY` branch of `SessionLifecycleManager.resume` (the `if state == SessionState.EMPTY:` arm) delegates to `_append_message_to_previous_turn`, which (a) no-ops for turn `01` (no predecessor report ever exists) and (b) for mid-session `EMPTY` turns (`>01`) appends `## User Request` to the predecessor report WITHOUT re-evaluating that turn's preservation into `session.context`. The fix adds a turn-`01` sub-branch writing to `initial_request.md` AND a re-preservation call (`preserve_turn_in_session_context`) after the mid-session append. Recent commits on the file: `4ad20f2d`, `ba2e5ff4`, `0f35baa9`, `2b09bd92`.

### Environmental Triggers
None — both defects are pure CLI/session-state logic with no OS-specific behavior, and reproduce deterministically. All verification (MREs, regression test, full suite) ran on macOS / Python 3.13.14.

## Diagnostic Analysis
### Causal Model
Confirmed by reading + MRE. `create_session` (`session_service.py`) writes `initial_request.md` and seeds its root-relative path into `session.context` at creation. `get_session_state` classifies by artifact presence: `report.md` present → `COMPLETE_TURN`; else `plan.md` present → `PENDING_PLAN`; else `EMPTY`. After `teddy start` is quit before the first plan, turn `01` has neither artifact → `EMPTY`.

`_orchestrate_session_loop` threads the injected `-m` message into `SessionLifecycleManager.resume` on the first iteration only (then clears it). The `EMPTY` branch calls `_append_message_to_previous_turn(turn_path, message)`, which computes `parent/00` and no-ops because `00/report.md` never exists for turn `01`. The message is then threaded transiently into `_handle_planning_and_execution` → `SessionPlanner.trigger_new_plan` → `PlanningService.generate_plan(user_message=message)` → `PromptManager.resolve_message(message, turn_path)`, which returns the message verbatim (the `initial_request.md` fallback at `prompt_manager.py:58` only fires when `user_message is None`). So the augmented request never reaches `initial_request.md` — the durable artifact present in `session.context` — and is not persisted anywhere durable for turn `01`.

For `COMPLETE_TURN`, `resume` calls `_append_user_request` (writes `## User Request` into the turn's `report.md`), then `transition_to_next_turn` → `_is_preserved_turn` detects that heading and appends the turn's `plan.md`/`report.md` to `session.context`, so that path DOES persist the message. Hence Hypothesis A (turn `01`) is the real defect; Hypothesis B is already satisfied for `COMPLETE_TURN`.

For the mid-session `EMPTY` case (turn `>01`), the current turn is the empty successor `N+1` pre-created by turn `N`'s finalize. `_append_message_to_previous_turn` appends `## User Request` to turn `N`'s `report.md`, but turn `N`'s OWN preservation decision already ran inside `transition_to_next_turn` at the moment it created turn `N+1` — i.e. BEFORE this append. Nothing re-evaluates `_is_preserved_turn` after the append, so turn `N` is never added to `session.context`; the request is recorded durably in `report.md` (so it is not lost like the turn-01 case) but is not promoted to the prune-exempt session scope. Both the turn-01 and the mid-session defects are instances of the same class: a resume `-m` consumption site that either has no durable write target or performs its durable write AFTER the preservation decision has already been evaluated.

### Discrepancies
- Hypothesis B ("`resume -m` is never kept in `session.context`"). Conflict: the `COMPLETE_TURN` path DOES preserve the message via `_append_user_request` + `_is_preserved_turn`. (Resolved: B holds only for the `EMPTY`/turn-01 case, which is the same defect as A; the message is not persisted for turn 01 because `_append_message_to_previous_turn` no-ops. Fixing A — appending to `initial_request.md`, which is already seeded into `session.context` — also satisfies B for turn 01.)
- User (Turn 13): "aside from first turn … that turn that now includes a user request should be preserved. I believe it probably currently does not? I believe it does get preserved if we provide additional message through TUI 'm'?" Conflict: the `COMPLETE_TURN` path preserves, so the mid-session `EMPTY(>01)` path was assumed to preserve too. (Resolved: CONFIRMED via the mid-session MRE (Turn 24) — the `EMPTY(>01)` append does NOT re-evaluate preservation, so the augmented turn is absent from `session.context`; the TUI `m` path IS preserved because it renders the request before finalization. A `preserve_turn_in_session_context` re-evaluation after the append fixes it.)

## Solution

### Root Cause

`SessionLifecycleManager.resume` consumes an injected `-m` message on three arms, but only the `COMPLETE_TURN` arm durably persists it in a way that reaches the prune-exempt `session.context`. The `EMPTY` arm delegates to `_append_message_to_previous_turn`, which has two failure modes:

1. **Pre-first-plan (`EMPTY`/turn `01`):** the helper computes the predecessor turn (`01` → `00`) and no-ops because `00/report.md` never exists — turn `01` has no predecessor. The injected message is threaded only transiently into the imminent plan generation (`_handle_planning_and_execution` → `SessionPlanner.trigger_new_plan` → `PlanningService.generate_plan` → `PromptManager.resolve_message`, which returns the injected message verbatim and never reads `initial_request.md`). The augmentation is therefore never written to `initial_request.md` — the durable artifact already seeded into `session.context` — so a later bare `resume` falls back to the stale request and the message never enters `session.context`.
2. **Mid-session (`EMPTY`/turn `>01`):** the helper appends `## User Request` to the predecessor turn `N`'s `report.md`, but turn `N`'s OWN preservation decision already ran inside `transition_to_next_turn` when it created the empty successor `N+1` — i.e. BEFORE this append. Nothing re-evaluates `_is_preserved_turn` afterwards, so turn `N` (and its freshly-appended request) is never re-admitted to `session.context`. The request is durable in `report.md` but remains subject to turn-scope pruning.

By contrast, the `COMPLETE_TURN` arm calls `_append_user_request` and THEN `transition_to_next_turn`, so `_is_preserved_turn` sees the `## User Request` and preserves the turn; and the TUI `m` path renders the request into `report.md` before finalization, so it is likewise preserved. Both defects are the same class: a resume `-m` consumption site that either has no durable write target or performs its durable write AFTER the preservation decision has already been evaluated.

### Verified Fix (As-Built)

Three coordinated changes; the mid-session half required one ADDITIVE, non-breaking extension to the `ISessionManager` Protocol (the earlier "no Port/signature/DTO change" claim in this Case File was inaccurate and is corrected here).

1. **Turn-`01` (`EMPTY`) branch** (`session_lifecycle_manager.py`): when the current turn is `01`, append the injected message to the session's durable `initial_request.md` via a new `_append_to_initial_request` helper (smart-fenced `## Additional Request` section, mirroring `_append_user_request`) instead of the always-no-op `_append_message_to_previous_turn`. Because `initial_request.md` is already seeded into `session.context` at creation, this single change satisfies both coupled hypotheses (A: message lost before first plan; B: message absent from `session.context`) for turn `01`. Proven via Shadow File MRE — Investigation History #4 (exit 1 → exit 0).
2. **ADDITIVE Protocol member** (`session_manager.py` + `session_service.py`): `ISessionManager.preserve_turn_in_session_context(turn_dir)` was added (additive, non-breaking) and implemented on `SessionService` as a faithful mirror of `transition_to_next_turn`'s preservation arm — re-runs `_is_preserved_turn` (now matching `## User Request`) then `_append_to_session_context`. The lifecycle manager reaches it solely through the Protocol (`SessionPorts.session_service` is typed `ISessionManager`).
3. **Mid-session (`EMPTY`/turn `>01`) branch** (`session_lifecycle_manager.py`): after a successful `_append_user_request`, re-evaluate the predecessor turn's preservation via `self._session_service.preserve_turn_in_session_context(prev_turn)`, admitting the augmented turn to the prune-exempt session scope. Proven via Shadow File MRE — Investigation History #6 (mid-session MRE exit 1 → exit 0; the turn-01 MRE remains exit 0).

**Contract-double migration:** the hand-written `DummyManager` in `tests/suites/unit/core/ports/test_session_manager_contract.py` enumerates Protocol members by hand, so the additive member required a one-line migration (it failed `isinstance(...)` until updated). All other consumers use `create_autospec`/`register_mock`, which auto-tolerate additive members; a `git grep` census confirmed `DummyManager` was the sole affected double.

**Regression test:** `tests/suites/unit/core/services/test_session_lifecycle_resume_message_persistence.py` pins both failure modes against the REAL `SessionLifecycleManager`/`SessionService`, asserting on observable file effects (`initial_request.md` / `session.context` contents) rather than internal call sequences. RED before the fix (2 failed on their own assertions + 1 control passing) → GREEN after (3 passed). Both original MREs, repointed at production (shadow import dropped), exit 0. Full suite: 1618 passed / 5 skipped, 0 failed.

### Systemic Preventative Measures

The defect class is "a resume `-m` injection site whose durable write does not reach the prune-exempt `session.context`" — either because there is no durable write target (turn `01`) or because the write happens after the turn's preservation decision was already evaluated (mid-session). The durable pattern: every branch of the resume state machine that consumes an injected message MUST end by ensuring the message is both (a) written to a session-scoped artifact and (b) reflected in `session.context`. The Phase 4 Systemic Audit `git grep`-ed the resume state machine and confirmed the `EMPTY` arm was the ONLY defective consumption site (the `COMPLETE_TURN` arm and the pipeline `AWAITING_REPLY` arm already write before the preservation decision). Follow-up debt surfaced by the audit — extracting the shared preservation helper (so `transition_to_next_turn` and `preserve_turn_in_session_context` cannot diverge), replacing the hand-written contract double with an autospec, and extracting the shared in-memory filesystem fake — is logged to `docs/project/PROJECT.md` under `## Technical Debt` for Milestone 5.
