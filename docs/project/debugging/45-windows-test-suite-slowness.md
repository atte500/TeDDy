# Bug: Test Suite Slower on Windows Than macOS
- **Status:** Resolved
- **Milestone:** N/A (ad-hoc)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms
The full `make test` run takes substantially longer on Windows 11 than on macOS. The user reports that certain tests in particular seem very slow. Expected behavior is comparable wall-clock time across platforms for the same serial test work.

## Context & Scope
### Regressing Delta
No single regressing commit. The slowdown is platform-conditional. The pytest-httpserver default host (`localhost`) interacts with the Windows IPv6-first loopback connect path. Four litellm retry tests also pay real backoff sleeps on every platform.

### Environmental Triggers
- Windows 11 host with `cmd.exe` as the default shell.
- `pytest` addopts in `pyproject.toml`: `-n auto`, `--import-mode=importlib`, `--timeout=5`.
- CI raises the pytest timeout to 15s when `CI=true`.

### Ruled Out
- DNS and `getaddrinfo` cost, which is 0ms for both `localhost` and `127.0.0.1`.
- Proxy resolution, because IP-addressed requests complete in 2-3ms under the same default environment.
- Server handling and fixture startup, which cost 9-10ms and answer IP requests in 2ms.
- pyfakefs setup cost, which is 3ms per cycle and affects only 33 test functions.
- Cold `litellm` import per worker. The harness replaces `sys.modules["litellm"]` with a Mock before any test imports it, and `trafilatura` is never loaded, so the 3.57s figure measured outside pytest never appears in suite wall-clock time.

## Diagnostic Analysis
### Causal Model
Measured on this Windows 11 host (12 logical CPUs, Python 3.12.9). Fixed per-worker costs are real but bounded: twelve workers each pay a cold `litellm` import near 3.57s, `trafilatura` 0.61s, `mistletoe` 0.25s, and one `git status --porcelain` shell-out near 40ms. Per-test autouse work is negligible near 0.15ms. The pyfakefs term is 3ms per cycle after the first cycle and only 33 test functions request the `fs` fixture, so pyfakefs is not a suite-scale cost and the earlier 0.79s reading was cold-import overhead. The dominant per-test cost is a single fixed wait near 2.0s attached to each real loopback HTTP request addressed by hostname. Every openrouter test that issues one request costs 2.02-2.06s, while the two cache-hit tests that start the same `httpserver` fixture without issuing a request cost 0.01s, which places the cost in the request and not in the fixture. On the same server port, a raw socket connect to `localhost` costs 2035-2057ms while the identical connect to `127.0.0.1` costs 0ms, `getaddrinfo` costs 0ms for both hosts, and `urllib` plus `requests` reproduce the split, so the cost is the hostname connect path rather than name resolution, transport, or server handling. The pytest-httpserver plugin resolves its listen host from the `PYTEST_HTTPSERVER_HOST` environment variable and falls back to `localhost` (`HTTPServer.DEFAULT_LISTEN_HOST`), and `url_for` interpolates the constructed host into every served URL. No `--httpserver-host` flag exists, so the environment variable is the only override. The raw resolver order is `::1` before `127.0.0.1`, the server binds IPv4 only, and constructing the server with `host="127.0.0.1"` collapses a request from 2037ms to 1ms. Four litellm retry tests pay exactly 1.50s because the adapter computes `delay = 0.5 * (2**attempt)` in `_should_retry_completion` and the tests never inject a time service, so three attempts sleep 0.5s then 1.0s on real `time.sleep`. Together these 19 tests carried roughly 36s of the 40.87s serial run of 296 tests.

The remedy is verified end to end. Pinning `PYTEST_HTTPSERVER_HOST=127.0.0.1` in `tests/conftest.py` collapsed the two formerly slow modules from 31.37s to 0.40s. An A/B run of the full suite measured 45.87s with the old `localhost` default against 28.93s with the pin, a suite-level delta of 16.94s on this host. The serial outbound subset fell from 40.87s to 8.95s. The four litellm tests at 1.50s each are the only remaining serial wait. That wait is platform-independent, and a paired spike measured 1.50s on the real clock against 0.00s with a recording `ITimeService` fake that captured the `[0.5, 1.0]` backoff schedule. The `ILlmClient` factory in `registries/infrastructure.py` now passes `time_service=container.resolve(ITimeService)`, and the four named retry tests inject a recording fake that asserts the `[0.5, 1.0]` schedule, so no retry path sleeps on the real clock.

The serial phase decomposition is now measured. A plugin that aggregates every phase report recorded 94.55s of session wall clock against a 95.68s pytest-reported duration: 8.17s setup over 1,875 reports, 66.39s call over 1,842 reports, and 16.92s teardown over 1,875 reports. Process creation cost 1.73s across 148 spawns, and temporary workspace churn cost 0.31s across 295 `mkdtemp` and 279 `rmtree` calls. The call histogram holds 1,342 tests under 5ms and 170 tests at or above 100ms, and the slowest tests are acceptance, session-handler, and integration cases at 0.5-1.1s. Most serial time therefore sits inside the test bodies and in the teardown phase, not in coverage, process creation, or workspace creation.

The parallel and syscall attribution run invalidated itself. Loading a plugin that wraps `os.stat`, `open`, `os.mkdir`, and `time.sleep` produced 29 failures under `-n auto` and 28 under `-n 6`, against a known green baseline of 1,839 passed. The worker reports also contradicted each other: twelve workers reported five call phases between them, two reported none, and one finished at `+61.26s` in a `65.18s` run. The operation table then attributed 65,397 `stat` and 10,682 `mkdir` calls to the collection bucket instead of to tests, so its measured seconds describe controller startup rather than the suite. A serial rerun with the per-test timeout disabled reproduced 29 failures in 106.99s, so the wrapper breaks tests independently of the five-second guardrail. The failures concentrate in the two YAML config adapter modules, the recursive file-system listing, the prompt resource lookup, the reviewer wiring, and the action executor, which are exactly the modules that read real files behind the pyfakefs patcher. The single-process counters are unusable for a second reason: nested opens were charged on every call, which reported 181.24s inside 12,739 opens, a figure larger than the whole run. Every syscall figure from this instrumentation is permanently withdrawn, and module-level os wrapping is rejected as an attribution technique for this suite.

The uninstrumented worker curve bounds the parallel ceiling. The suite costs 93.65s at one worker, 56.53s at two, 35.12s at four, 36.95s at six, 28.70s at eight, and 29.35s at twelve. Eight workers is the floor, so the default twelve adds no throughput, and the single six-worker sample sits above the four-worker result, which is either noise or a scheduling artifact. A two-term fit over the one-worker and eight-worker points yields roughly 19s of fixed wall-clock cost plus 74s of parallelizable work, and that fit predicts 25.2s at twelve workers against 29.35s measured. Most of the shortfall against the eight-second ideal therefore follows from the fixed term rather than from the worker count. The curve cannot distinguish CPU saturation from blocked workers, so the fixed term is not yet attributed.

The machine's own throughput curve separates hardware capacity from suite behavior. Independent single-threaded CPU-bound processes released behind a barrier reach 1.00x at one process, 2.01x at two, 3.00x at three, 3.96x at four, 5.36x at six, 5.33x at eight, 5.84x at ten, and 6.06x at twelve, so this six-core, twelve-thread Ryzen 5 3600 caps near its physical core count and SMT adds little for pure Python loops. Efficiency is 100% through four processes, 89% at six, 67% at eight, and 50% at twelve. The suite reaches 3.26x at eight workers and 3.19x at twelve, which is 61% and 53% of the machine curve at the same process counts. The suite therefore loses about half the machine throughput, and the earlier reading that the plateau is a pure hardware ceiling is retired. A serialized controller whose per-test cost scales with the test count, worker contention on a shared resource, or a workload mix that scales worse than a tight integer loop can each produce that loss, and the machine curve alone cannot separate them.

The scheduling sweep measured dispatch volume and withdrew the controller-load figure. Holding eight workers fixed, the default per-test scheduler costs 28.08s while `loadfile` costs 24.79s, `loadscope` 24.55s, and `worksteal` 23.98s, and every mode stays green at 1,839 passed, so chunked dispatch removes 3.3-4.1s of wall clock. Four workers with `loadfile` cost 31.55s, so the eight-worker width stays ahead. The controller CPU sampler reported 0.00s for the first run and 0.02s for the rest. A controller that dispatches and collects 1,875 reports cannot spend twenty milliseconds of CPU over twenty-five seconds, so the sampler never read the process times and every utilisation figure is withdrawn. A three-term fit of `C + W/n + n*S` to the two-, four-, and eight-worker points returns `C` near 5.2s, `W` near 97s, and `S` near 1.4s, and it predicts 30.5s at twelve workers against 29.35s measured. A per-worker additive term implies that each extra worker costs wall clock as well as helping, which staggered worker startup would produce when the controller spawns workers in sequence.

The corrected worker timeline attributes the parallel wall clock. At twelve workers with default dispatch, workers start between 0.95s and 3.00s after the controller session starts, every first test begins at 5.54-5.55s, the makespan is 27.95s, the summed work is 162.51s, and aggregate utilisation is 48%. At eight workers with worksteal dispatch, first tests begin at 4.13-4.14s, the makespan is 23.18s, the summed work is 142.78s, and utilisation is 77%. The identical first-test epoch across all workers is a collection barrier. xdist dispatches no test until every worker finishes collection, so the earliest worker waits 4.59s while the last worker waits 2.55s.

Import contention is falsified. A bare interpreter costs 0.04s serially and 0.10s at twelve-way concurrency, a bare pytest import costs 0.26s and 0.59s, and importing the root conftest costs 0.37s and 0.75s. Twelve simultaneous harness imports therefore add at most 0.4s over the serial figure, which cannot fill a 2.4-4.6s gap.

The repeated dispatch comparison confirms the gain and sizes collection. Twelve workers with default dispatch cost 30.58s and 30.68s, worksteal at the same width costs 25.71s and 25.41s, and eight workers with worksteal cost 26.13s and 26.21s. The gain is therefore 5.07s at twelve workers and 4.46s at eight workers, with a run-to-run spread below 0.3s. Collection alone costs 2.83s at twelve workers and 2.72s at eight workers for 1,875 tests. Collection occupies the last 2.7-2.8s of the barrier, and worker spawn occupies the earlier 0.95-3.0s, which together reproduce the 5.5s first-test epoch.

The Windows wall clock at twelve default workers now decomposes fully. The run spends 5.5s in the pre-test barrier, executes in a 27.95s makespan, and leaves 2.9s outside the reconstructed session window. The makespan delivers 5.81x aggregate concurrency against the host's 6.06x machine ceiling, which is 96% of that ceiling even when every measured work second is treated as CPU-bound. The remaining distance to the reported 15s on macOS therefore follows from host capacity, because the same 91.48s of serial work runs on faster cores with a higher parallel ceiling. Dispatch mode is the only suite-side lever left, and it is worth 5.07s.

## Solution
### Root Cause
The slowdown is the interaction between the pytest-httpserver default listen host and the Windows dual-stack loopback path. The server binds the IPv4 literal only, while `localhost` resolves to `::1` first on Windows. Every request addressed by hostname therefore wastes about two seconds on a failed IPv6 connect before the IPv4 fallback answers. The 19 openrouter tests that issue a request carried roughly 36s of the 40.87s serial outbound subset, and the 22-test openrouter module pair fell from 31.37s to 0.40s once the host was pinned. The Windows-specific suite delta is 16.94s, measured as 45.87s against 28.93s in an A/B run. A second wait is platform-independent: four litellm retry tests never inject `ITimeService`, so three attempts sleep the real 0.5s and 1.0s backoff. The loopback fix was applied directly, touching `tests/conftest.py` and its matching test file. The litellm backoff fix was proven in a sandbox spike (`spikes/debug/windows-test-suite-slowness/04-time-service-retry-proof.py`), which showed 1.50s on the real clock against 0.00s with a recording fake and a captured schedule of `[0.5, 1.0]`. Slice 00-46 then shipped that fix: the factory injects the time service and the four named tests assert the recorded schedule.

The residual Windows wall clock is not a second defect. Twelve default workers spend 5.5s in a pre-test barrier of staggered spawn plus whole-session collection, then execute 162.51s of summed work in a 27.95s makespan, then finish with a 2.9s tail. The makespan reaches 96% of the host's measured 6.06x parallel ceiling. The macOS comparison is inferred from that ceiling, because no Mac is available to measure the same suite, and faster cores with a higher ceiling applied to the same 91.48s of serial work explain the reported 15s. Chunked dispatch at `--dist worksteal` recovers 5.07s at twelve workers, measured across two repeats with a spread below 0.3s.
