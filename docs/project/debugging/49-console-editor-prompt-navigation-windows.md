# Bug: Console editor confirm prompt loses cursor navigation on Windows

- **Status:** Resolved
- **Milestone:** N/A
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms

**Expected behavior:**
At the `Editor opened. Terminal reply or [Enter] to confirm editor ›` prompt (console ask loop), Left/Right arrow keys plus Alt+Left/Right and Ctrl+Left/Right word-jumps navigate the input cursor, matching the behavior of the preceding `Response (type 'e' for editor) ›` prompt.

**Actual behavior:**
On Windows, after the editor flow (`e` -> editor opens), the confirm-editor prompt does not respond to Left/Right, Alt+Left/Right, or Ctrl+Left/Right navigation. The immediately preceding prompt navigates correctly within the same session.

**Minimal reproduction steps:**
1. On Windows, start a console session.
2. At `Response (type 'e' for editor) ›` type `e` and press Enter.
3. Editor opens (observed: `codium.CMD`); prompt becomes `Editor opened. Terminal reply or [Enter] to confirm editor ›`.
4. Attempt Left/Right (and Alt/Ctrl+Left/Right): cursor navigation does not work.

**Platform:** Windows 11 only. MacOS: not reproducible (navigation works at both prompts).

## Context & Scope

### Regressing Delta

No TeDDy code regression — the fault is a Windows-only interaction between three long-standing behaviors, not a recent commit: (1) the ask loop's zero-gap re-prompt design — `_launch_editor_background` fires the GUI editor via fire-and-forget `subprocess.Popen(codium.cmd)` sharing the parent console, and `run()` immediately re-enters `_pt_prompt` while the codium.cmd→cmd.exe→node chain is still initializing; (2) prompt_toolkit's per-session, capability-gated `Vt100ConsoleInputReader` selection plus one-shot `ENABLE_VIRTUAL_TERMINAL_INPUT` enable (raw_mode) with no mid-session re-assertion (source-confirmed); (3) the editor chain's console-input-mode mutations during init (observed: mid-session write 487 and a dirty non-ptk state 992 right after the live session ended). The "delta" is the platform execution environment (shared win32 console / ConPTY), not a code change.

### Environmental Triggers

- OS: Windows 11 (bug absent on MacOS).
- Console ask loop editor flow: editor opened first, then the "Terminal reply or [Enter] to confirm editor" prompt.
- Editor command observed by user: `codium.CMD` (VSCodium batch launcher).
- `codium`/`code` are NOT in `_CLI_EDITORS`, so the ask loop takes the GUI path: `subprocess.Popen(editor_cmd + [temp_path])` (fire-and-forget) followed immediately by `_flush_stdin()`, which on Windows drains the input buffer via `msvcrt.kbhit()`/`msvcrt.getwch()` before the next `ptk_prompt` call.
- User's host terminal application identified: the **VSCodium integrated terminal** (ConPTY-based; the ConPTY host is the VSCodium/Electron process itself). The user runs sessions directly in the codium terminal.
- Repro Python: CPython 3.12.9 (uv-managed) with prompt_toolkit from the project `.venv`.

### Ruled Out

- **Divergent input mechanism between the two prompts (original Hypothesis B):** code read of `console_interactor_ask_loop.py` shows both prompt strings are rendered by the same `ConsoleAskLoop.run()` loop through the same `_pt_prompt()` helper, which calls `ptk_prompt(prompt_text, history=self._history)` whenever `sys.stdin.isatty()`. The two prompts are NOT served by different input mechanisms.
- **Textual/TUI subsystem:** the `textual_plan_reviewer_*.py` grep hits ("Opening Editor", "for editor") belong to the Textual plan reviewer app (`app.notify`), a different inbound adapter from the console ask loop the user reported.
- **Fresh regression in ask-loop code:** the last 5 commits (through c71c8fc) touch only `system_environment_inspector.py`, release files, and the parser — no recent delta in `console_interactor_ask_loop.py` or editor tooling. The bug is more likely a long-standing platform interaction than a fresh regression.
- **Console-mode corruption breaking nav (refined):** in the real terminal the codium chain cleared only ENABLE_MOUSE_INPUT (503→487); nav still worked under that mode. Mouse-flag changes are real but not the culprit mechanism.
- **Buffer junk (FOCUS events, stray key-up records) poisoning ptk nav:** disproven by probe v3 Stage 2 — nav worked with both pending in the buffer.
- **The probe's simplified sequence itself (Popen codium.cmd + flush → next ptk prompt):** empirically insufficient to trigger the bug in the real terminal; the trigger requires a production-only delta (see Causal Model D1–D4).
- **os.system('') / SetConsoleMode console resets in the production ask path (D4 sub-hypothesis):** repo-wide grep found neither anywhere in src/; the only console-touching code in the ask path is the ask loop's own `_flush_stdin` (plus the Textual plan-reviewer editor's POSIX flush — a different subsystem). The PROJECT.md debt note citing os.system at ask-loop lines 173-174 is stale — those lines now hold the subprocess.Popen GUI-editor spawn.
- **ConsoleInteractor wrapper interference in the ask path:** `ask_question` = header print (typer → stderr) + `ConsoleAskLoop.run()`; no console-state manipulation. `restore_terminal_mode()` (POSIX-only) is not called in the ask path (only `confirm_action` calls it).
- **Double `_flush_stdin` as the arrow-eater:** production flushes twice back-to-back (once inside `_launch_editor_background` after Popen, once again in `run()`), but both complete BEFORE the 'Editor opened' ptk session starts (MRE v1 logged both `[flush]` lines before the S2 session-start marker, and the S2-start buffer peek was EMPTY). The flushes cannot consume keys pressed during the live session.
- **Shared InMemoryHistory (D1) as the delivery mechanism:** the arrow loss occurs at prompt_toolkit's input layer (`Win32Input.read_keys` yields no arrows), which is independent of application-level prompt history. D1 cannot remove arrow INPUT_RECORDs before the key processor.
- **Header print / surrounding-session output (D4') as a REQUIRED trigger:** the MRE included the faithful typer/stderr header print and still reproduced; the full app's session-output context is not necessary for reproduction (it may still modulate the trigger in the live app).
- **ConPTY host non-delivery of arrow keys (branch c):** no longer required to explain the symptom — the dirty post-S2 mode (992) plus the MOUSE clear prove the codium chain mutates the shared console mode mid-session, and the VT100 reader's `'\x00'` drop fully accounts for the arrow loss with chars unaffected. Delivery failure is not needed.
- **Flush/buffer pollution of any kind:** definitively dead — buffer verified empty at S2 start in both v1 and v2 while the bug reproduced.
- **prompt_toolkit re-checking the live console mode when choosing its input reader (self-healing path):** disproven by source — `_is_win_vt100_input_enabled()` is a one-time capability probe and the reader is fixed per session regardless of the live mode (empirically corroborated: the broken S2 session dropped arrows — impossible under the legacy `ConsoleInputReader` + VT-off pairing, which maps VK arrows fine).
- **prompt_toolkit re-asserting/repairing the console mode mid-session:** disproven by source — `raw_mode` sets the mode once at session entry and restores the entry snapshot at exit; no mid-session re-assertion exists to overwrite the editor chain's mutations.
- **Persistent console corruption requiring cleanup between prompts:** the chain's mutations are transient; a fresh session after the chain quiesces re-establishes VT and navigates fine (NAV-POST WORKS) — no durable corruption exists to clean.
- **`start_new_session=True` isolating background shell spawns from the console on Windows:** disproven — it is a POSIX-only subprocess feature (setsid) and is silently ignored on win32; background shell commands inherit the parent console there (stdio DEVNULL only redirects the three standard streams, not console attachment).

## Diagnostic Analysis

### Causal Model

Updated after synthetic MRE probe (turn 02→03): Both prompts share the identical prompt_toolkit path, so the fault must be persistent cross-call state. The synthetic probe (fresh conhost) established empirically that: (1) the console input mode is NOT altered by the `codium.CMD` chain or the production flush in that environment (mode stable at 487 post-control-child; VT input never set; flush drained 0); (2) ENABLE_VIRTUAL_TERMINAL_INPUT alone does not break ptk navigation; (3) the WriteConsoleInputW injection harness itself is invalid as a navigation discriminator (injected VK_LEFT records ignored by ptk at pristine baseline, while VT-translated ESC[D sequences work). The synthetic conhost therefore does not reproduce the user's real terminal. Remaining leading hypothesis (refined): a **delivery-format mismatch at the prompt_toolkit input boundary in the user's real terminal** — after the editor flow, arrow keys reach prompt_toolkit in a different encoding than before (e.g., as VT char-event sequences instead of VK key events, or not at all), breaking all arrow-based navigation while leaving character typing intact. The user's host terminal application (Windows Terminal / classic conhost / VS Code integrated) is now a critical unknown, since ConPTY-based terminals deliver input differently from conhost. Next probe: user-mediated manual run of `spikes/debug/49-manual-console-probe.py` inside the real terminal, which raw-logs INPUT_RECORDs (VK, UnicodeChar, ControlKeyState) for Left/Right/Ctrl+Left plus ptk nav verdicts and console-mode snapshots, before and after the production editor spawn. Update (turn 05): the host terminal is now known to be the VSCodium integrated terminal (ConPTY-based). The delivery-format-mismatch hypothesis is refined with ConPTY-specific candidate mechanisms: (a) escape-sequence/OSC emission by the `codium.cmd` child into the shared ConPTY input pipeline that survives or desynchronizes the msvcrt drain (msvcrt `getwch` consumes whole key INPUT_RECORDs, not bytes — it can partially consume or mis-align record sequences), (b) host-injected focus/resize input events when the new VSCodium window opens, (c) ConPTY input-translation state changes after the child exits (e.g., VT input enabled so arrows arrive as ESC[D char events that ptk's win32 reader mishandles). The first probe attempt crashed from probe-induced ctypes argtypes pollution (now fixed); the actual measurement is still pending. Additional structural observation (turn 06): the production `_flush_stdin()` runs immediately after `subprocess.Popen(editor_cmd + [temp_path])` — before the `codium.CMD` child has even started executing — so it cannot drain anything that lands in the console input buffer afterwards (e.g., host-terminal responses to editor-emitted queries, or focus events, which the msvcrt drain does not consume anyway). Probe v3 therefore adds non-consuming `PeekConsoleInputW` buffer dumps at every stage boundary plus a temporary wrapper around prompt_toolkit's `Win32Input.read_keys` logging every key press ptk's input layer yields, so a single user-mediated run can discriminate: (i) arrows not delivered at all, (ii) delivered in a different encoding, (iii) delivered as VK records but dropped inside prompt_toolkit, or (iv) leftover buffer junk poisoning prompt_toolkit's key processor state.
Probe v3 result (turn 07→08): the user-mediated run in the real VSCodium terminal did NOT reproduce the bug — post-editor nav WORKS in the probe's simplified sequence, in the very terminal where production fails. The codium chain's only console-mode effect was clearing ENABLE_MOUSE_INPUT (503→487), which is nav-benign. Pending FOCUS events and a stray Enter key-up record were also nav-benign (hypothesis (iv) is dead for these event types). The fault therefore lives in a production-only delta the probe did not model: (D1) the ask loop shares ONE InMemoryHistory across both prompts (probe used a fresh history per nav test), changing ptk's history-browsing state machine; (D2) production re-prompts IMMEDIATELY after Popen+flush (no settle), so the codium.cmd→cmd.exe→node chain runs WHILE the 'Editor opened' ptk session is already live — junk arriving mid-session interacts with a live key processor rather than sitting in the buffer before the session starts; (D3) production's find_editor()/temp-file/logging side effects; (D4) surrounding session context (ConsoleInteractor wrapper, possible os.system('') console resets elsewhere in the interactor family, prior session output). Next step: a production-fidelity MRE driving the real ConsoleAskLoop class with ptk read_keys logging, plus D1/D2-variant minimal replications, run by the user in the real terminal.
Recon result (turn 08→09): the production ask path contains NO console-state manipulation beyond `_flush_stdin` itself — no os.system(''), no SetConsoleMode, no wrapper interference (the os.system debt note is stale; current code uses subprocess.Popen). `ask_question` adds only a typer/stderr header print before prompt 1; `find_editor()` is a pure shutil.which resolution. The probe-vs-production divergence therefore reduces to: (D1) shared InMemoryHistory across both prompts; (D2) zero-gap re-prompt — production's second ptk session starts IMMEDIATELY after Popen+flush while the codium.cmd→cmd.exe→node chain is still running, so host-terminal arrivals (e.g., FOCUS events) hit a LIVE key processor mid-session (the probe's 5s settle meant everything landed before session 2 started and was provably benign); (D3) find_editor/temp-file/logging side effects; (D4') surrounding session output context (header print, Rich/LLM streaming output). Next probe: `spikes/debug/49-askloop-mre.py` loads the real ask-loop module file directly, drives the real ConsoleAskLoop (faithful find_editor re-implementation + faithful header print) with per-session tagged key-yield logs, GetConsoleMode+PeekConsoleInputW at every session boundary, _flush_stdin logging, and a post-run raw INPUT_RECORD log — user-mediated in the VSCodium terminal. run()'s return value doubles as the nav verdict ('BA' = not reproduced → D4' implicated; 'AB' = reproduced → D1/D2/D3 bisectable).
MRE result (turn 10→11): the production-fidelity MRE REPRODUCED the user-reported symptom (user-confirmed broken navigation at the live 'Editor opened' prompt) while the settled simplified probe v3 did not. Established facts: (1) production flushes twice back-to-back, both BEFORE the S2 session starts (buffer empty at S2 start) — the flushes cannot consume mid-session arrows; (2) prompt_toolkit's input layer yielded ZERO arrow presses during the live S2 session while chars and Backspace yielded normally, and LEFT/RIGHT arrive as normal VK records once the session ended — the loss is at/below the input layer and confined to the live-session window; (3) the console mode flipped 503→487 (mouse cleared) DURING the live S2 session — the codium.cmd→cmd.exe→node chain acts on the shared console while ptk is live. D2 (zero-gap re-prompt) is the prime trigger candidate by elimination (D1 input-layer-implausible; D3 inert; header print included in the MRE and it still reproduced). Four candidate mechanisms for the missing arrows: (a) stolen by another console-input reader in the chain; (b) consumed by ptk and silently dropped by its record→key mapping; (c) never delivered by the ConPTY host while the chain is live; (d) transient console-mode flips (e.g., temporary ENABLE_VIRTUAL_TERMINAL_INPUT) that the boundary snapshots missed. MRE v2 design: a unified timeline watcher thread polling GetConsoleMode + GetNumberOfConsoleInputEvents + non-consuming PeekConsoleInputW every 10ms across the whole run; a within-run NAV0 standalone ptk nav baseline BEFORE the loop; a NAV-POST fresh-session recovery test AFTER the loop (splits session-bound vs persistent breakage); timestamped read_keys call logging in one timeline; plus a read of ptk's `input/win32.py` to locate silent-drop paths (per-read mode-dependent decoding, ESC assembly, modifier-based drops).
MRE v2 timeline result (turn 12→13) — unified mechanism: prompt_toolkit's `Vt100ConsoleInputReader._get_keys` (read at turn 11) yields ONLY records with `u_char != '\x00'`, silently discarding VK-only key records — the exact record form of arrow/navigation keys when `ENABLE_VIRTUAL_TERMINAL_INPUT` is off. ptk's `raw_mode` enables VT input during each prompt session (watcher mode=1008 during working NAV0/S1 sessions; arrow yields carried VT data `'\x1b[D'`). The production zero-gap re-prompt starts the 'Editor opened' session while the `codium.cmd`→cmd.exe→node chain is still initializing; the chain's console init mutates the shared console input mode mid-session (MOUSE cleared 503→487 at t≈1.2s into S2; dirty raw-ish mode 992 with VT ON immediately after S2 ended), flipping the session into the inconsistent state (VT100 reader + VT-off mode) in which arrows are delivered as VK `'\x00'` records that the VT100 reader silently drops, while typed characters (non-null UnicodeChar) pass through. The watcher's blindness during live ptk sessions (GIL starvation — zero entries during NAV-POST which provably required VT mode) explains why no 1008 window was seen during S2. Retroactive explanations: the synthetic conhost baseline BROKEN verdicts (WriteConsoleInputW-injected VK records carry `'\x00'` and are dropped by the VT100 reader regardless of editor/state), and probe v3's non-repro (5s settle → chain console init completed before session start → ptk's VT-enable persisted → consistent state). Fix direction (refined after source confirmation, turn 13→14): desynchronizing the re-prompt from the editor chain's console-init window (settle before the 'Editor opened' ptk session) is empirically validated (probe v3) but timing-fragile — the chain can mutate the shared mode at any point during a long-lived session (mid-session write observed ~1.2s after spawn; dirty non-ptk state right after session end). Source-level confirmation (turn 13): prompt_toolkit selects its Windows input reader ONCE per prompt session via `_is_win_vt100_input_enabled()`, a capability probe that attempts `SetConsoleMode(hconsole, ENABLE_VIRTUAL_TERMINAL_INPUT)` and restores the original mode — it never inspects the live mode at prompt time, so on Windows 11 the `Vt100ConsoleInputReader` serves EVERY session even when the live mode has VT off. `raw_mode` is one-shot: `__enter__` captures the mode and `_patch` sets `original & ~(ENABLE_ECHO|ENABLE_LINE|ENABLE_PROCESSED) | ENABLE_VIRTUAL_TERMINAL_INPUT` (exactly the watcher's 1008 = 503 & ~7 | 0x200 during working sessions); `__exit__` restores the entry snapshot; nothing re-asserts the mode mid-session. The observed S2 breakage itself confirms the reader pairing: under the legacy `ConsoleInputReader` + VT-off pairing arrows would map fine from VK codes — the silent-drop signature is unique to the VT100-reader + VT-off mismatch. Candidate fixes: (F1) isolate the GUI editor spawn from the parent console on Windows (detached/no-console creation flag on the fire-and-forget Popen) — the chain can then never read or write our console mode, eliminating the entire interference class instead of racing it; (F2) adaptive quiesce-wait (poll GetConsoleMode until stable, capped) before re-prompting — validated in principle by probe v3 but fragile against late mutations; (F3) one-shot mode re-assertion is insufficient by construction (cannot protect mid-session clears). F1 is the systemic candidate; verification via Shadow File + user-mediated run after RCA approval.
Systemic audit census (turn 16, post-approval): the interference class is "fire-and-forget child spawn that inherits the parent console while an interactive prompt can be live". Three unflagged instances exist: (1) the ask-loop GUI editor Popen (proven bug site); (2) `SystemEnvironmentAdapter.run_command(background=True)` — GUI diff-viewer spawns via `ConsoleInteractor._handle_external_preview`, same codium.CMD chain class, also the mechanism family behind the editor escape-leak bugs #24/#27/#28/#44; (3) `ShellAdapter._run_subprocess(background=True)` — `start_new_session=True` is POSIX-only (ignored on Windows), and stdio DEVNULL only redirects the three standard streams, not console attachment. The fix pattern is `subprocess.CREATE_NO_WINDOW` under `sys.platform == "win32"`, mirroring `textual_plan_reviewer_editor.py` (production-proven). Synchronous spawns stay unflagged (safe by construction: no live session during the child; the next session re-establishes VT — NAV-POST evidence). Shadow verification of site (1) is the Zero-Touch gate; sites (2)/(3) receive the same pattern in the implementation turn with unit-level regression assertions on the Popen kwargs, since the live race is only exercisable at the editor site.

## Solution

**Root cause (Windows-only, three-actor race):** (1) prompt_toolkit selects its Windows input reader once per prompt session via `_is_win_vt100_input_enabled()` — a capability probe (attempt `SetConsoleMode(ENABLE_VIRTUAL_TERMINAL_INPUT)`, restore) that always succeeds on Windows 10+, so every session is served by `Vt100ConsoleInputReader`, which silently discards key records whose UnicodeChar is `'\x00'`; (2) `raw_mode` enables VT input one-shot at session entry and never re-asserts it mid-session; (3) the console ask loop's GUI fire-and-forget `subprocess.Popen(codium.CMD)` lets the editor's launcher chain inherit and mutate the shared console, and the zero-gap re-prompt starts the 'Editor opened' session while the chain is still initializing. The chain clears VT input mid-session (observed 503→487 during the live session), leaving the inconsistent state (VT100 reader + VT-off mode) in which arrows arrive as `'\x00'` VK records that are silently dropped — typing and Backspace keep working (real characters), navigation dies. MacOS is unaffected (no win32 console mode for a child to mutate; prompt_toolkit reads the tty directly).

**Proven fix (Zero-Touch verified):** on Windows, spawn the GUI editor detached from the parent console by passing `creationflags=subprocess.CREATE_NO_WINDOW` to the fire-and-forget `Popen` — the chain gets its own invisible console and can never read or write ours, eliminating the entire interference class instead of racing it. Verified without touching production code via a byte-faithful shadow replica (headless FIX CHECK: `creationflags == 134217728` VERIFIED) and a user-mediated live run in the real VSCodium terminal (verdict 'BA', arrows yielded as VT sequences, no mode mutation). This mirrors the production-proven `spawn_editor()` pattern already used in `textual_plan_reviewer_editor.py`.

**Systemic fix (user-mandated generalization):** apply the same Windows `CREATE_NO_WINDOW` guard to every fire-and-forget spawn site in `src/` — the ask-loop GUI `Popen` (the bug site), `SystemEnvironmentAdapter.run_command(background=True)` (GUI diff-viewer launches), and `ShellAdapter`'s background path (whose `start_new_session=True` is POSIX-only and does not detach consoles on Windows). Synchronous spawns (CLI editors, foreground commands) are excluded by design: they run while no prompt session is live and CLI editors need the real console. Side benefit: the chain's console output/escape sequences also stop reaching the user's terminal (the same interference family behind the editor escape-leak bugs #24/#27/#28/#44).

**Preventative measure (class-level):** the repo-wide rule is that any fire-and-forget child spawn on Windows MUST be detached from the parent console (`CREATE_NO_WINDOW`) whenever an interactive prompt session can be live concurrently. This was codified by extending the existing pattern from `textual_plan_reviewer_editor.py` to all three audited spawn sites, with unit-level regression assertions on the Popen kwargs pinning the behavior.
