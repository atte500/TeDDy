# Bug: `resume -m` Interactive (No-Pipeline) Reply Not Consumed

- **Status:** Resolved
- **Milestone:** N/A (ad-hoc)
- **Vertical Slice:** [00-21-session-interrupt-resume-message.md](/docs/project/slices/00-21-session-interrupt-resume-message.md)
- **Specs:** [interactive-session-workflow.md](/docs/project/specs/interactive-session-workflow.md)

## Symptoms

**Expected:** After an interrupted pipeline turn (`teddy start -p` stopped on a MESSAGE, leaving `meta.yaml` with `awaiting_reply: true` and no `report.md`), resuming with a supplied reply SHOULD inject that reply as the awaited response and drive the next turn — identically whether or not `-p` is passed.

**Steps:**
1. `uv run teddy start -p -m "Say hi and ask how I am"` — pipeline turn stops; `01/meta.yaml` has `awaiting_reply: true`, no `report.md`.
2. `uv run teddy resume -m 'response'` (interactive, WITHOUT `-p`).

**Actual:** the supplied reply is NOT consumed as the awaited response (behaviour diverges from `teddy resume -p -m 'response'`, which works).

## Context & Scope

### Environmental Triggers
Resume of an `awaiting_reply` session in INTERACTIVE mode (no `-p`) while supplying `-m`. Comparison baseline: same resume WITH `-p`.

### Ruled Out
- `SessionLifecycleManager._consume_awaiting_reply` reply threading — `reply = message` short-circuits all "no reply" branches whenever `message` is non-empty, independent of `pipeline` (read at HEAD). NOT the divergence site unless `message` never reaches it.
- CLI option binding in `__main__.py` — the `resume` command forwards `message=message` and `pipeline=pipeline` INDEPENDENTLY to `handle_resume_session`, which forwards both verbatim to `_orchestrate_session_loop` → `orchestrator.resume` (read at HEAD). `message` is NOT gated on `pipeline` at the CLI layer.
- CLI `OPT_*` option objects — `OPT_PIPELINE`/`OPT_NO_COPY`/`OPT_UI_MODE` are plain `typer.Option(...)` definitions with no default/callback that could gate `message` (read at HEAD, `__main__.py:110-116`).
- Planning + state-resolution layers — `SessionPlanner.trigger_new_plan` passes `message` straight through to `PlanningService.generate_plan(user_message=...)`; `PromptManager.resolve_message` returns a non-empty `user_message` verbatim; `SessionService.get_session_state` routes PENDING_PLAN to the awaiting-reply check (read at HEAD). No `pipeline`/`interactive` branching exists in any of these.

## Diagnostic Analysis

### Causal Model
Full dispatch chain: CLI `resume` (`__main__.py`) → `handle_resume_session(message=..., pipeline=...)` → `_orchestrate_session_loop(message=..., pipeline=...)` → `SessionOrchestrator.resume(...)` → `SessionLifecycleManager.resume(...)` → (PENDING_PLAN + `awaiting_reply`) `_consume_awaiting_reply(...)`.

Every link read at HEAD forwards `message` to the next link UNCONDITIONALLY — none gates it on `pipeline`. Inside `_consume_awaiting_reply`, `reply = message` is assigned FIRST, so whenever `message` is non-empty the three fallback branches (`not reply and interactive` prompt; `not reply and pipeline` stop-again; bare `not reply` guidance) are ALL skipped, and the SAME consumption path runs for both modes: clear flag via `save_turn_meta` → `_synthesize_message_report(reply=reply)` → `finalize_turn` → `_handle_planning_and_execution(..., message=reply)`. Static reading therefore predicts PARITY between interactive and pipeline resume.

The ONLY genuine difference between the two modes is downstream of consumption: `interactive`/`pipeline` reach `orchestrator.execute` (turn-02 plan review vs. auto-approval) — NOT whether the reply is consumed. A `-p`-gated divergence in reply consumption is thus UNEXPLAINED by static reading.

EMPIRICAL CONFIRMATION (T7 MRE `spikes/debug/57-resume-message-interactive-mre.py`): driving the REAL `SessionLifecycleManager.resume` for both modes produced PARITY — both consumed the reply (planning `message=REPLY`, report `details=REPLY`, flag cleared, no prompt). The lifecycle layer is therefore NOT the divergent site. The diverging site (if any) must be in a layer the MRE MOCKED (`orchestrator.execute` / `trigger_new_plan` / `get_session_state` / the CLI `_orchestrate_session_loop`) OR the real scenario's state differs from `PENDING_PLAN+awaiting_reply`.

[T10] `SessionOrchestrator.resume` (read at HEAD) is a CLEAN PASSTHROUGH — `return self._lifecycle_manager.resume(session_name, self, interactive, project_context=project_context, message=message, pipeline=pipeline)` — it gates nothing on `pipeline` for reply consumption; `_is_pipeline_message_stop` only gates the pipeline-stop FINALIZATION on the pipeline-start path. So every link from CLI → handler → loop → wrapper → lifecycle consumer forwards `message` unconditionally. The remaining un-inspected site is the INTERACTIVE-LOOP CONTINUATION in `session_cli_handlers._orchestrate_session_loop`: the loop clears `message = None` after the first `orchestrator.resume`, and the pipeline break (`if pipeline and report.action_logs:`) means only PIPELINE resumes terminate — an interactive resume RE-ENTERS `orchestrator.resume(message=None)`. This re-entrancy is the leading remaining hypothesis for the `-p`-gated divergence.

[T11] `session_cli_handlers._orchestrate_session_loop` (read at HEAD) forwards `message`/`pipeline`/`interactive` to `orchestrator.resume` and clears `message = None` immediately AFTER the first resume — so the injected reply IS delivered to the first resume and cannot be re-sent to later turns. `handle_resume_session` forwards `message=..., pipeline=...` verbatim; `_resolve_session_name` resolves a no-path resume to the latest session. `ProductionSessionLoopGuard.should_continue` returns `(True, None)` unconditionally when `interactive=True`, and the loop's only `-p` discriminator is the trailing `if pipeline and report.action_logs:` MESSAGE-break. NEITHER path drops the reply; the asymmetry is continuation policy, not reply delivery. Static model is now COMPLETE and predicts PARITY.

## Solution
**Root cause (CONFIRMED, T20; verified RED→GREEN, T22/T23).** `SessionLifecycleManager.resume` handles a `PENDING_PLAN` turn by two disjoint paths: with `awaiting_reply` it routes to `_consume_awaiting_reply`; WITHOUT the flag it re-executes the plan via `orchestrator.execute(plan_path=..., interactive=..., pipeline=...)`. Only the pipeline-stop path SETS `awaiting_reply`. An INTERACTIVELY-interrupted MESSAGE turn (plan.md written, execution interrupted before `report.md`, flag never set) therefore lands in `PENDING_PLAN` WITHOUT the flag and takes the re-execute branch — which does NOT forward the injected `-m` message, never reaches `trigger_new_plan`, re-executes the existing turn plan, and (in interactive mode) the MESSAGE action re-prompts via `ask_question` ("Response (type 'e' for editor) ›"). The user's `resume -m` thus dropped the reply instead of consuming it. (This is orthogonal to `-p`: the reported symptom was the interactively-interrupted turn state, NOT the pipeline flag — which is why every harness that modelled `PENDING_PLAN + awaiting_reply` showed parity.)

**Fix (VERIFIED zero-touch via Shadow File, T23).** Route an injected `message` on a COMMUNICATION (single-MESSAGE) `PENDING_PLAN` turn through the EXISTING `_consume_awaiting_reply` semantics — change the guard from `if turn_meta.get("awaiting_reply"):` to `if turn_meta.get("awaiting_reply") or (message and self._is_communication_turn(turn_path)):`. This unifies the two "MESSAGE turn awaiting a reply" states (pipeline-stopped WITH the flag; interactively-interrupted WITHOUT it): the reply finalizes the interrupted turn (`- **User Reply:** <reply>`) and drives the next turn's planning, mirroring the awaiting path exactly. A `resume` with no `-m` (interactive) and non-communication `PENDING_PLAN` turns retain today's behaviour.

**Preventative / systemic.** A communication turn is semantically "awaiting a reply" whether it was stopped by the pipeline or interrupted interactively, yet only the pipeline path records that state — so `resume` must infer intent from a missing flag PLUS the plan shape. The durable fix is a single source of truth for the "interrupted-at-a-reply" state, set on BOTH stop paths, so the resume state machine has one branch instead of a two-factor inference. Log as a follow-up guard.

**Systemic Audit (Phase 4).** *Abstract class:* a state-machine transition keyed off a marker recorded on only ONE of several paths that reach the same logical state — i.e. an under-specified state representation at a state boundary. *Census (`git grep`):* the `awaiting_reply` flag has exactly ONE producer — `session_orchestrator.py:318-324` (the pipeline-stop path) — and two consumers — `session_lifecycle_manager.py:73` (resume guard) and `:209` (consumption pop); there is no third writer. `SessionService.get_session_state` (`session_service.py:176-195`) derives `PENDING_PLAN` purely from "plan.md exists AND report.md absent", so an interactively-interrupted MESSAGE turn and a pipeline-stopped MESSAGE turn are indistinguishable on disk EXCEPT for the flag. The `orchestrator.execute` audit confirms the non-awaiting `PENDING_PLAN` branch (`session_lifecycle_manager.py:85`) is the ONLY call site that re-executes a pending turn's plan WITHOUT forwarding a message. *Impact:* the fix is a single-file internal guard change (plus the `_is_communication_turn` helper) with NO Port/Signature/DTO consumer to migrate → TRIVIAL, no Vertical Slice, no Contract→Migration partition. *Generalized prevention:* give the "interrupted-at-a-reply" state a single source of truth set on BOTH stop paths (logged as `[DEBT]` in PROJECT.md; Milestone 5 slice).
