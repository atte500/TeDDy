# Bug: EditMatcher cannot anchor multi-line FIND blocks on partial fragments of long single lines

- **Status:** Resolved
- **Milestone:** [docs/project/milestones/05-quality-gate-debt-reconciliation.md](/docs/project/milestones/05-quality-gate-debt-reconciliation.md)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms

**Expected behavior:**
A multi-line FIND block whose lines are partial fragments of long single lines (e.g., a Case File Investigation History entry, which is a single ~1500-character line) matches the containing line(s) and applies the edit, reporting a high Similarity Score.

**Actual behavior:**
The matcher rejects the edit with a low Similarity Score (observed: 0.12 against the 0.95 threshold), even though the fragment text appears verbatim inside the file. Observed live during Case File 49 (turns 21/23/25 EDIT validation failures on the same Case File).

**Minimal reproduction steps:**
1. Target a file containing a very long single line (e.g., a Case File Investigation History entry).
2. Submit an EDIT whose FIND block is multi-line, with its first line being a mid-line fragment of that long line (e.g., the tail ~90 characters of the ~1500-character entry).
3. Validation fails with `Similarity Score: 0.12` despite the fragment being an exact substring of the file.

**MRE confirmation (this case file):** `spikes/debug/50-editmatcher-multiline-fragment-mre.py` reproduces the symptom against the live SUT: multi-line fragment FIND scores **0.21** (< 0.95) while the identical fragment as a single-line FIND scores **1.0** via the substring boost.

## Context & Scope

### Regressing Delta

Not a regression — a design limitation of the EditMatcher, discovered during the Case File 49 harness meta-audit (CF49 turn 27, user-requested). `find_best_match()` in `edit_matcher.py` is line-window based: the FIND block is split into lines and candidate windows of equal line count are scored via `difflib.SequenceMatcher` over the joined text. The only sub-line support, `_apply_substring_boost()`, fires ONLY when the FIND block is a single line; the Tier 3 candidate enumeration in `edit_matcher_heuristics.py` likewise only handles `num_find_lines == 1`.

### Environmental Triggers

- Multi-line FIND block (>= 2 lines) where at least one line is a partial fragment of a long single-line file entry.
- Any target file with very long single lines — TeDDy Case Files (Investigation History entries) produce exactly this shape routinely, making agent-driven Case File edits prone to this failure.

### Ruled Out

- **TeDDy EDIT pipeline correctness bug:** the CF49 turn-27 audit proved the validator (`validation_rules/edit.py`) and the executor (`edit_simulator.py`) both delegate to the same `find_best_match()`; validation and execution cannot diverge, and the reported 0.12 score is the genuine, mathematically correct score for that input (approximately 2·M/(len(window)+len(find)) for a ~100-char fragment against a ~1500-char line window).
- **CRLF / line-ending normalization:** ruled out — anchors strip whitespace, the substring boost rstrips `\r\n`, and CRLF only marginally affects multi-line ratio computation.

## Diagnostic Analysis

### Causal Model

For a multi-line FIND block, candidate windows are scored by joining the window lines and the FIND lines and running `difflib.SequenceMatcher.ratio()`. When a FIND line is a short fragment of a very long file line, the joined-window text is dominated by the unrelated remainder of that line, so the ratio degenerates to approximately fragment_length / line_length (observed 0.12). The substring boost that would rescue this case (score 1.0 for an exact intra-line substring match) is gated on `len(find_lines) == 1`, so multi-line FIND blocks never receive it; Tier 3 anchor enumeration correspondingly never considers intra-line positions for multi-line FIND blocks. Net effect: partial-line anchoring works only for single-line FINDs.

**Refinement (MRE-verified):** candidate *generation* is not the proximate failure for small files — Tier 4's exhaustive fallback (`set(range(len(file_lines) - num_find_lines + 1))`) already generates the correct line-aligned window start; the degenerate *joined-window scoring* in `_evaluate_candidates`/`_refine_and_select_best` is what rejects it. However, for large files the single-line-only Tier 3 gate is a *secondary* failure: without it, the correct window start may never become a candidate (Tier 1 requires full-line equality; Tier 2's fuzzy first-line cascade degenerates against ~1500-char lines), so both the scoring path and the Tier-3 gating must be generalized.

**Verified fix mechanism (Shadow-proven, REVISED per user alignment — text-editor find & replace semantics):** the substring boost gains a multi-line branch that fires only when the ENTIRE FIND block appears VERBATIM as a contiguous substring of the candidate window (`"".join(find_lines) in "".join(window)`), returning the literal FIND block as the match (`match_lines = [find_text]`). This is exact text-editor behavior: (1) a multi-line FIND starting at a mid-line fragment and running through the end-of-line plus following full lines matches at 1.0 and replaces exactly the found text (line head preserved); (2) a mid-line fragment followed by a newline does NOT match, because the file line continues after the fragment; (3) a single-line fragment still matches intra-line via the unchanged single-line branch. Ambiguity is flagged when the literal multi-line block occurs more than once within the window. NO heuristics changes are required: literal multi-line FIND blocks always contain full middle lines that Tier 1's exact full-line anchors already locate (Tier 3 remains single-line-only). The single-line branch is preserved byte-for-byte; the returned literal block trivially satisfies EditSimulator's `content.replace()` contiguity contract.

## Solution

**Root cause:** the EditMatcher's only sub-line rescue path (`_apply_substring_boost`) and the Tier 3 intra-line anchor enumeration were gated on `len(find_lines) == 1` / `num_find_lines == 1` — a capability keyed to a structural shape rather than its semantics. Multi-line FIND blocks therefore degenerated to joined-window `difflib` ratios (~0.12–0.68 against long single lines), far below the 0.95 threshold, even when the FIND text appeared verbatim in the file. A design limitation (not a regression) discovered during the Case File 49 harness meta-audit.

**Proven fix (literal text-editor find & replace semantics, user-confirmed):** a single `elif` branch appended to `_apply_substring_boost()` in `src/teddy_executor/core/services/validation_rules/edit_matcher.py` — fires only for multi-line FIND blocks (`len(find_lines) > 1`, window size equals FIND size, ratio still < 1.0) and rescues the match at 1.0 when the ENTIRE FIND block appears VERBATIM as a contiguous substring of the candidate window (`"".join(find_lines) in "".join(window)`), returning the literal FIND block as the match. Newlines inside the FIND must correspond to real file line breaks; starting/ending mid-line is otherwise fine. Ambiguity is flagged when the literal block occurs more than once within the window. The single-line branch is preserved byte-for-byte. The returned literal block trivially satisfies EditSimulator's `content.replace()` contiguity contract. No changes to heuristics, simulator, or validator.

**Verification:** zero-touch shadow verification (`spikes/debug/shadow_edit_matcher.py` + `shadow_edit_simulator.py`, byte-for-byte replicas with only the import changed) passed all five locked semantics end-to-end: (A) literal multi-line FIND starting mid-line → 1.0 + surgical simulator round-trip preserving the ~600-char line head; (C) mid-line fragment + claimed newline → correctly rejected (0.21); (B) single-line fragment control → unchanged 1.0; (D) multi-line FIND ending mid-line without terminator → 1.0 verbatim; (E) same shape with trailing newline → correctly rejected (0.09).

**Performance:** the branch executes only on the ≤5 capped refinement candidates, only for multi-line FINDs with ratio < 1.0, costing one string join + one native O(n+m) substring search per candidate — strictly cheaper than the `difflib.SequenceMatcher.ratio()` call already executed on the identical strings. Exact multi-line matches (the common case) skip the branch entirely; single-line FINDs take the identical code path as before.

**Preventative measures (systemic, class-wide):** the bug class is "a capability gated on a structural shape rather than its semantics." Recurrence prevention: (1) any shape-gated fast path or boost in the matcher MUST justify its gate by semantics, not a line-count singularity — a `len(...) == 1` gate requires a comment or test stating why the capability is genuinely single-input-only; (2) the regression test suite locks the full text-editor find & replace semantics (scenarios A–E), so future matcher changes that silently narrow or widen matching behavior fail the suite; (3) a categorical `git grep` audit for line-count gates is part of the review checklist for any future EditMatcher change.
