# Bug: Intermittent Windows CI Worker Crash
- **Status:** Resolved
- **Milestone:** N/A (ad-hoc regression)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms
The `Test Suite (windows-latest)` job fails on the `Run Tests` step and reports one failed test against 2102 passed and 36 skipped. The victim differs across runs. Run `6a4800cc` crashed `tests/suites/acceptance/test_session_management.py::test_teddy_resume_continuous_loop`, and run `38ed373d` crashed `test_start_fast_forwards_a_behind_workspace` and `test_history_log_append_mode`. The xdist worker dies with `node down: Not properly terminated`, and the controller reports `worker '...' crashed while running ...`. The step log contains no traceback and no fatal-exception marker. The Linux and macOS legs pass in the same runs (for example run 40202571457).

Reproduction: run the CI workflow on `windows-latest`. The failure is intermittent and needs a transiently degraded runner, so a healthy host does not reproduce it.

## Context & Scope
### Regressing Delta
No single commit regressed the victim tests, because the victim changes across runs. The amplifier is the 15 second CI per-test budget introduced by `f2877865` ("fix(tests): implement dynamic timeout scaling for CI environments"). Commit `ca2fc614` ("test(timeouts): give subprocess-heavy suites their own budget") raised two earlier victims to 30 seconds, which was still insufficient. Commit `8deaf61a` had previously removed `.with_real_interactor()` from sibling acceptance tests, but the crash class is independent of the interactor.

### Environmental Triggers
Windows (win32) with pytest-xdist (`-n auto --dist worksteal`) on a four-CPU `windows-latest` runner. On Windows, pytest-timeout uses the `thread` method because `SIGALRM` is unavailable. A transient runner stall must push one test past the per-test budget.

### Ruled Out
- The non-blocking `Quality Checks` job is not the cause. The workflow marks it `continue-on-error: true`.
- A normal pytest assertion failure is not the cause. The worker exits hard before pytest renders a failure.
- Cold-start cost is not the cause. The cold full-suite run passed in 29.72 seconds with 2103 tests.
- Ordinary contention is not the cause. Three exact CI-command repetitions passed in 25.08, 24.11, and 27.32 seconds.
- The daemon update-check fetch is not the sole cause. It runs off-thread with a 10 second socket timeout.
- The interactive interactor is not the cause. The crash moves across tests that use different input paths.

## Diagnostic Analysis
### Causal Model
The Windows CI leg intermittently lost an xdist worker. The pytest-timeout `thread` method calls `os._exit(1)` when a test exceeds the per-test budget. That hard exit fails the whole suite on whichever test was running. The old CI budget was 15 seconds, set inside `tests/conftest.py`. Three different acceptance tests crashed across runs, so no single test owns the defect. A controlled 20 second stall reproduced the exact `[gw1] node down: Not properly terminated` line at a 15 second budget. The same stall passed at a 60 second budget, so the budget decides the outcome. Four consecutive full-suite runs on windows-latest passed, which shows cold start and ordinary contention do not trigger the stall. A transient host condition is the remaining trigger. The verified remediation raises the shared CI per-test budget to 60 seconds through one harness constant. It also adds a 10 minute job wall-clock cap, so a genuine hang still terminates the job.

## Solution
### Root Cause
The failure is not a test-local defect. On Windows, pytest-timeout uses the `thread` method because `SIGALRM` is unavailable, and the timer calls `os._exit(1)` when a test exceeds the per-test budget. The worker dies, and the suite fails on whichever test was running. The CI budget was 15 seconds, so a transiently degraded runner could push one test past it. The [controlled stall proof](/spikes/debug/windows-ci-worker-crash/test_stall_budget_proof.py) reproduced `[gw1] node down: Not properly terminated` at `--timeout=15` and passed at `--timeout=60`, which proves the budget is the amplifier. The [thread-method signature experiment](/spikes/debug/windows-ci-worker-crash/test_timeout_signature.py) shows xdist discards the timer output, which explains the missing traceback. Four consecutive full-suite runs on windows-latest passed (29.72 seconds cold, then 25.08, 24.11, and 27.32 seconds), so the trigger is a transient host condition rather than cold start or ordinary contention. The remediation was applied directly to test infrastructure, because no production file under `src/` is involved. `make test` passed with 2137 passed and 5 skipped.

### Affected Components
- `tests/harness/setup/timeouts.py` (new): single source of truth for the shared CI per-test budget and its activation rule.
- `tests/conftest.py`: `pytest_configure` reads `ci_per_test_timeout()` instead of hardcoding 15 seconds, and the dead string literal was removed.
- `tests/suites/acceptance/test_workspace_start_pull.py`: the subprocess-heavy marker rose from 30 to 60 seconds.
- `tests/suites/integration/core/services/test_session_orchestration_integration.py`: the module-level marker rose from 30 to 60 seconds.

- `tests/suites/unit/test_ci_timeout_budget.py` (new): pins the CI-only activation, the absent local value, and the headroom over an observed stall.
- `docs/architecture/ARCHITECTURE.md`: the CI Pipeline law states the shared-budget and job-cap requirement.
- `docs/templates/ci.md`: the template demonstrates the job cap and the budget pairing.
