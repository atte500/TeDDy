# Bug: CPR Escape Sequence Leak into Console Reply Prompt
- **Status:** Resolved
- **Milestone:** N/A (ad-hoc)
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms
- **Expected:** Upon receiving an agent message, TeDDy renders the interactive reply prompt `Response (type 'e' for editor) › ` and waits for a clean, user-typed reply.
- **Actual:** A warning is printed — `WARNING: your terminal doesn't support cursor position requests (CPR).` — and a raw escape-sequence fragment (`[17;1R`) leaks onto the prompt line, appearing as pre-typed input that the user must delete.
- **Reproduction:** Run `teddy start`, reach the "awaiting reply" prompt after an agent message, and observe the warning + leaked fragment at the `Response (type 'e' for editor) ›` prompt.

## Context & Scope
### Regressing Delta
The concurrent single-byte stdin consumer introduced by the quit-key work is the regressing delta (one file: `src/teddy_executor/adapters/outbound/terminal_quit_key_listener.py`). `d741b41a` (slice 00-21, session-interrupt-resume-message) introduced `TerminalQuitKeyListener` — a daemon thread reading stdin one byte at a time (`os.read(fd, 1)`), guarded ONLY by a check-then-read `is_stdin_owned()` test. Bug 58 (slice 00-23, q-interrupt-mid-execution) then made that reader PERSISTENT (`_read_loop` keeps polling for the whole session; see the `_read_loop` docstring in the file) in commit `b0a18211` ("interrupt in-flight action on q and persist the quit-key reader"). Before this reader existed there was no competing stdin consumer, so prompt_toolkit's CPR reply reached its parser intact. **Root-cause category (abstract):** a check-then-read TOCTOU (time-of-check-to-time-of-use) race around a shared resource — a non-atomic guard (the `is_stdin_owned()` test) followed by a blocking acquisition (`select()` + `os.read()`), where the guarded state can change in the window between the two operations. The regression is the check-then-read TOCTOU window in `_read_one_byte_posix`: once the loop's guard has passed, the blocking `select()` + `os.read(...)` consume a byte with no re-check, so a byte that becomes readable only AFTER the ask prompt claims stdin (the CPR reply) is stolen. (Introducing/persistence commits confirmed via `git log` — see Investigation History.)

### Environmental Triggers
Requires a terminal emulator that responds to the Cursor Position Request escape sequence `ESC[6n`. The leaked payload `[17;1R` is the terminal's cursor-position reply (`ESC[<row>;<col>R` with row=17, col=1), stripped of its leading ESC. Exact terminal/OS combination to be pinned down.

### Ruled Out
- TeDDy's own source does NOT contain the warning text: a `git grep` over `src/` and `tests/` for `cursor position` / `CPR` / `doesn't support` matched only the prompt string in `console_interactor_ask_loop.py:143`. Therefore the warning is emitted by a dependency, not by TeDDy code.

## Diagnostic Analysis
### Causal Model
The console reply prompt is served by `ConsoleAskLoop._pt_prompt` (`src/teddy_executor/adapters/outbound/console_interactor_ask_loop.py:117-121`), which delegates to `prompt_toolkit.shortcuts.prompt` while `ConsoleAskLoop.run` holds `stdin_owned()` for the whole prompt (`:136`). On a TTY, prompt_toolkit's `Application` sends a Cursor Position Request `ESC[6n` at startup (`output/vt100.py:713`) and waits for the terminal's reply `ESC[<row>;<col>R`, parsed by `input/vt100_parser.py:22` (regex `^\x1b\[\d+;\d+R\Z` — the leading ESC is REQUIRED).

CONCURRENTLY, TeDDy's persistent `TerminalQuitKeyListener` thread (`terminal_quit_key_listener.py:79-98`) runs a continuous poll loop that checks `is_stdin_owned()` ONCE and then blocks in `select()`, consuming one byte at a time via `os.read(fd, 1)`. There is a check-then-read TOCTOU gap: the listener checks ownership (False, just before the prompt begins), then blocks in `select`; the prompt then claims `stdin_owned()` (True) and issues the CPR; the terminal's reply makes stdin readable; the listener's `select` fires and `os.read` steals the FIRST byte — the `ESC` (0x1b) — which `_process_byte` discards (≠ QUIT_KEY 0x71). prompt_toolkit then reads `[17;1R` (no leading ESC), which cannot match `_cpr_response_re`, so it is rendered as literal typed input; meanwhile the CPR wait times out and calls `cpr_not_supported_callback`, printing the warning. Both observed symptoms are caused by the listener stealing exactly one byte.

VERIFIED FIX (Zero-Touch, Turn 7): re-checking `is_stdin_owned()` AFTER `select()` reports the fd readable but BEFORE `os.read(...)` (and before `msvcrt.getwch()` on Windows) closes the race. The shadow replica `spikes/debug/shadow_terminal_quit_key_listener.py` (byte-for-byte copy of the real module with ONLY that re-check added to both readers) makes the MRE print `LISTENER_CONSUMED_BYTE: None` and `PROMPT_WOULD_READ: b'\x1b[17;1R'` → `VERDICT: OK (listener backed off; full CPR reply intact)`. The re-check is sound because the CPR reply only becomes readable AFTER the prompt claims stdin and sends `ESC[6n`, so the post-`select` re-check reliably observes ownership (the residual check→read window is a few bytecodes, far shorter than a real terminal round-trip) and yields the bytes to prompt_toolkit.

### Discrepancies
- The warning states the terminal does NOT support CPR, yet the leaked fragment (`17;1R`) IS a syntactically valid CPR reply — so the terminal DOES support CPR. The warning therefore likely reflects a timing/timeout race (or stale/async reply), not genuine lack of support. (Resolved: emitter identified as prompt_toolkit 3.0.53 — `prompt_toolkit/application/application.py:1243`; the warning is a soft timeout notice, not a hard capability verdict.)
- Open question: why does the CPR reply (`ESC[17;1R`) end up as apparent TYPED input rather than being consumed/discarded by prompt_toolkit? Two candidate mechanisms: (a) the reply arrives after prompt_toolkit stopped waiting (timeout) and stays buffered for the next read, or (b) a concurrent reader (TeDDy's quit-key listener) drains/returns the bytes. (Resolved — identified as (b): the persistent `TerminalQuitKeyListener` steals the leading ESC byte via a check-then-read TOCTOU race; the reply reaching prompt_toolkit is `[17;1R` without its ESC, hence unparseable, and the same theft makes the CPR wait time out → warning. Empirical confirmation via MRE `spikes/debug/60-cpr-response-escape-leak-mre.py` — result recorded in Investigation History.)

## Solution

### Root Cause
A **check-then-read TOCTOU (time-of-check-to-time-of-use) race on stdin.** TeDDy's persistent quit-key reader (`TerminalQuitKeyListener`, introduced by `d741b41a` and made persistent by `b0a18211`) runs a background thread that polls stdin one byte at a time. It tested ownership (`is_stdin_owned()`) only at the TOP of each loop iteration and then performed a blocking `select()` + `os.read(fd, 1)`. Between that check and the read, the console ask prompt can claim stdin (`stdin_owned()`) and issue prompt_toolkit's Cursor Position Request (`ESC[6n`). When the terminal's reply (`ESC[17;1R`) became readable, the already-blocked reader woke and consumed its **first byte — the `ESC` (0x1b)** — which `_process_byte` discarded (it is not `q`). prompt_toolkit then received `[17;1R` without its leading `ESC`, which cannot match its CPR-response regex (`input/vt100_parser.py:22`, `^\x1b\[\d+;\d+R\Z`), so (a) its CPR wait timed out and it printed the "your terminal doesn't support cursor position requests (CPR)" warning, and (b) the orphaned fragment was rendered as literal typed input. **One stolen byte → two symptoms.**

### Verified Fix
Re-check `is_stdin_owned()` **after** readiness but **before** consuming the byte, in both readers:
- `_read_one_byte_posix`: insert `if is_stdin_owned(): return None` between `select.select(...)` and `os.read(fd, 1)`.
- `_read_one_byte_windows`: insert `if is_stdin_owned(): return None` between `msvcrt.kbhit()` and `msvcrt.getwch()`.

The re-check is sound because the CPR reply only becomes readable AFTER the prompt claims stdin and sends `ESC[6n`; at that instant ownership is already claimed, so the re-check reliably backs off and yields the bytes to prompt_toolkit. The residual check→read window is a few bytecodes — far shorter than a real terminal round-trip — so it cannot swallow the reply. Proven (Zero-Touch / shadow file `spikes/debug/shadow_terminal_quit_key_listener.py`): the MRE against the **real** module stole `ESC` (byte 27) and left `[17;1R`; against the **shadow** replica (only this re-check added) it consumed nothing and left the full `\x1b[17;1R`.

### Preventative Measures (this class of bug)
- **Categorical rule:** any non-atomic guard on a shared resource followed by a blocking acquisition (check-then-read) MUST be re-verified AFTER the acquisition point reports readiness but BEFORE the destructive operation. The `is_stdin_owned()` convention is now "check at the loop top **and again immediately before the read**."
- **Census result (this session):** `git grep` confirmed the quit-key reader is the ONLY persistent background stdin consumer; the other stdin sites (`console_interactor_ask_loop._flush_stdin`, `textual_plan_reviewer_editor` drain) are controlled `tcflush`/`msvcrt` drains that run only while the owner holds stdin, so they cannot race. No sibling instance required fixing.
- **Guardrail for future readers:** any new persistent stdin consumer MUST adopt the same post-readiness re-check before consuming a byte.
- **CPR suppression rejected as the primary fix:** setting `PROMPT_TOOLKIT_NO_CPR=1` would silence the warning but masks the entire concurrency class and disables cursor detection; the post-readiness re-check is the correct root-cause fix.
