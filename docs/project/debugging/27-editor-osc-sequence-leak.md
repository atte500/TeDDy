# Bug: Editor Escape Sequence Leak in Harvest Flow

- **Status:** Unresolved
- **Milestone:** N/A (ad-hoc slice 00-07)
- **Vertical Slice:** [00-07-editor-subsystem-overhaul.md](/docs/project/slices/00-07-editor-subsystem-overhaul.md)
- **Specs:** N/A

## Symptoms

When opening vim from the ask loop (typing `e`):

1. **Garbled text appears:** The user sees `]10;rgb:8080/8989/b3b3` displayed on the terminal after vim exits. This is an OSC escape sequence (set dynamic color) generated by the terminal emulator. Moving the cursor makes it disappear, but it is present when the prompt reappears.

2. **Harvest captures garbled text instead of editor content:** After exiting vim and pressing Enter, the garbled text `]10;rgb:8080/8989/b3b3` (or similar) is passed as the user message instead of the content from the temp file. The session log shows this as the initial request.

3. **Log shows full path instead of editor name:** The opening log says `Opening Editor: /usr/bin/vim` instead of `Opening Editor: vim`. This is cosmetic but confusing.

**Expected behavior:**
- No escape sequences should appear on the terminal after editor exit.
- Pressing Enter should harvest the content from the temp file.
- Log should show just the editor name (e.g., `vim`), not the full path.

**Actual behavior:**
- OSC sequence leaks onto the terminal.
- The leaked sequence is captured as user input (instead of editor content).
- Log shows full path.

## Context & Scope

### Regressing Delta
The entire editor subsystem was overhauled in slice 00-07 (6 deliverables). The current implementation:

- **`_launch_editor_background()`** in `console_interactor_ask_loop.py`: Creates a temp file, spawns editor via `subprocess.Popen` with TTY inheritance, stores `_active_editor_path`.
- **`_handle_empty_input()`**: When Enter is pressed with `_active_editor_path` set, reads the file, strips escape sequences, deletes the file, calls `_flush_stdin()`, returns content.
- **`_flush_stdin()`**: Calls `termios.tcflush(sys.stdin, termios.TCIFLUSH)` to flush the input buffer.

The issue is that `_flush_stdin()` is called AFTER the file is harvested. The OSC sequence is generated by the terminal emulator when vim exits and arrives on stdin before or during the next `ptk_prompt` call. The `_flush_stdin()` call should clear it, but either:
- The sequence arrives after the flush (between flush and the next `ptk_prompt`).
- The flush is not effective for all types of terminal events.
- The sequence is not captured in the stdin buffer that termios can flush.

### Environmental Triggers
- Terminal emulator (likely iTerm2, Kitty, or similar that sends dynamic color sequences).
- Vim (or Neovim) as the editor.
- OSC sequences triggered by vim leaving terminal in a specific state.
- Reproduces on macOS (Darwin) — likely also on Linux with similar terminal emulators.

### Ruled Out
- The `_strip_escape_sequences()` function works correctly for text content already read from the file (tested in unit tests). The issue is not about stripping from the file content, but about the sequence appearing on stdin.
- The `_flush_stdin()` method works in unit tests under TTY conditions but may not clear all buffer states.

## Diagnostic Analysis

### Causal Model
1. User types `e` → `_launch_editor_background()` spawns vim with TTY inheritance.
2. Vim takes over the terminal, user edits, exits.
3. Terminal emulator sends an OSC escape sequence (e.g., `ESC ]10;rgb:8080/8989/b3b3 ESC \`) to restore/reset dynamic colors. This sequence is written to the terminal output stream, not stdin.
4. **But:** the sequence might also be echoed back on stdin by the terminal (local echo) or could be injected by the terminal emulator into the input buffer when the editor exits.
5. The next `ptk_prompt()` call reads from stdin. Since `_flush_stdin()` hasn't been called yet (it's called in `_handle_empty_input` which runs only after the user presses Enter, NOT before `ptk_prompt` in `run()`), the sequence is captured as raw input.
6. The sequence `e` is stripped? No, the garbled text does not contain `e`. The sequence itself is `]10;rgb:...\` which doesn't include `e`. After stripping ANSI/OSC sequences, it becomes empty or partially stripped, but the user reports the garbled text is passed as the message. This suggests the sequence bypasses stripping because `_strip_escape_sequences` is only called on the `user_input` returned by `ptk_prompt`, and the sequence may be passed directly to `continue` loop behavior.
7. Looking at the code: in `run()`, `raw_input = self._pt_prompt(prompt_text).strip()` then `user_input = self._strip_escape_sequences(raw_input)`. If raw_input is `]10;rgb:8080/8989/b3b3`, after stripping it becomes `]10;rgb:8080/8989/b3b3` (the regex doesn't match it because it lacks ESC). Wait, the regex matches `\x1b\][^\x1b]*(?:\x1b\\|\x07)` — that requires `\x1b]` at the start. The user's garbled shows `]10;rgb...` without the opening ESC. So the ESC byte was stripped or consumed, leaving part of the sequence.
8. The remaining `]10;rgb:8080/8989/b3b3` does not match any action key (`e`), so `if user_input.lower() == "e":` is false.
9. `if user_input:` is True (non-empty), so `return user_input` returns the garbled text as the response.
10. The editor content is never harvested because `_handle_empty_input` is never called (the loop returned early with the garbled text).

**Root cause:** The ESC prefix of the OSC sequence gets stripped by terminal echo processing, leaving the tail `]10;rgb:...\` which enters the prompt as valid input, bypassing editor detection and harvest. The `_flush_stdin()` call never runs because the loop returns before `_handle_empty_input`.

**Additional issue (cosmetic):** `logger.info("Opening Editor: %s", editor_name)` where `editor_name = editor_cmd[0]` — if `editor_cmd` is `["/usr/bin/vim"]`, it logs the full path. Should use `os.path.basename()`.

### Discrepancies
- `_flush_stdin()` is called in `_handle_empty_input()` but the garbled sequence is captured by `ptk_prompt` before that function is reached. The flush timing is wrong.
- The regex `_ESCAPE_SEQUENCE_RE` requires `\x1b` prefix. If the ESC byte is stripped by terminal processing, the remaining string is not matched and not stripped.

### Investigation History
1. Code review: Identified timing issue — flush happens after harvest, but garbled sequence enters via ptk_prompt before harvest. Also regex does not match sequence missing leading ESC.

## Solution

(To be filled by the Debugger.)

**Proposed fix hypothesis:**
- Call `_flush_stdin()` immediately after `_launch_editor_background()` returns, before the next prompt in `run()`.
- Additionally, call `_flush_stdin()` at the TOP of `_handle_empty_input()` before reading the file.
- Update the regex to also match the tail of an OSC sequence if the ESC part was stripped (e.g., match `]10;rgb:` patterns starting with `]`).
- For the log: use `os.path.basename(editor_cmd[0])` to extract just the executable name.
