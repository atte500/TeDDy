# Bug: Ctrl+C (SIGINT) Not Firing During TeDDy Execution on the Host Terminal

- **Status:** Resolved
- **Milestone:** N/A (ad-hoc slice)
- **Vertical Slice:** [00-21-session-interrupt-resume-message.md](/docs/project/slices/00-21-session-interrupt-resume-message.md)
- **Specs:** N/A

## Symptoms

Verification steps 6 and 7 of the `session-interrupt-resume-message` slice are non-functional on the user's machine:

- **Step 6 (Ctrl+C during execution, two-phase drain):** `uv run teddy start`, approve a plan with a long `EXECUTE` (e.g. `echo one`, `sleep 5`, `echo two`), press Ctrl+C during the sleep. Expected: the in-flight command completes, the remaining actions are logged INTERRUPTED, `report.md` is created, and the process exits. Observed: nothing happens (per the user).
- **Step 7 (Ctrl+C while waiting, immediate exit):** press Ctrl+C during the planning LLM call ("Waiting for assistant to respond...") or during an `ask_question` prompt. Expected: immediate exit with no partial artifacts. Observed: nothing happens (per the user).

The user reports the behaviour "not working on my machine at all" and suspects a terminal keybinding configuration conflict, and explicitly requested this be tracked as a SEPARATE case file to be tackled with the Debugger independently.

## Context & Scope

### Regressing Delta
N/A — the interrupt wiring is the delivered feature under verification (`InterruptGuard` Seam → Migration → Wiring). No regression is presumed; the failure is at the real-terminal interaction layer, outside `typer.testing.CliRunner`'s reach.

### Environmental Triggers
- Host: macOS (Darwin 25.5.0), shell `/bin/zsh`.
- Exact terminal emulator + keybindings UNKNOWN — the user suspects a keybinding conflict preventing SIGINT delivery on Ctrl+C.

### Ruled Out
- The in-process `InterruptGuard` phase logic (WAITING raises; EXECUTING sets the flag; a second signal within the grace window escalates) — `tests/suites/unit/core/utils/test_interrupt_guard.py` passes.
- SIGINT handler installation/restoration at the session-loop boundary — `tests/suites/unit/adapters/inbound/test_session_loop_interrupt_wiring.py` passes.
- Shell child process-group shielding (`preexec_fn` setsid/setpgrp on POSIX) — characterized by `tests/suites/unit/adapters/outbound/test_shell_adapter_kwargs.py`.
- The `uv run` launch wrapper — a real-PTY probe (`spikes/debug/56-uv-sigint-probe.py`) delivered genuine kernel SIGINT to a python child BOTH directly and via `uv run python`; both received it (`[DIRECT] PASS` + `[UV_RUN] PASS` → `VERDICT: H1 REFUTED`). uv does not block or withhold the terminal's process-group SIGINT.
- Textual's own application-mode ISIG handling — a real-PTY probe (`spikes/debug/56-textual-isig-probe.py`) showed a CLEAN Textual exit fully restores ISIG (`A-CLEAN`: `PRE ISIG=ON` → `POST ISIG=ON` → post-exit ETX `GOT-SIGINT`). The TUI does not leak on its own; the leak requires a pre-corrupted terminal (`B-PRECORRUPT`).

## Diagnostic Analysis

### Causal Model
Two local, kernel-level PTY probes have now exonerated every layer BETWEEN the terminal and the guard, AND the guard itself:
  - Investigation History #3 (PTY MRE) proved the guard's phase logic and the child `setsid` shield are correct under real kernel-delivered SIGINT (WAITING raises; EXECUTING sets the drain flag and the in-flight child survives).
  - Investigation History #4 (H1 probe) proved the `uv run` launch layer DOES deliver genuine terminal SIGINT to its python child (`[DIRECT] PASS` + `[UV_RUN] PASS` → H1 REFUTED). uv does not block or withhold the child's signal.
Since the kernel delivers SIGINT to a foreground process under a real PTY AND `uv run` forwards it AND the guard reacts correctly, the fault lies in the terminal/pty STATE itself — i.e. Ctrl+C is not GENERATING SIGINT on the user's machine:
  - H2 (TeDDy terminal-mode leak — strongest TeDDy-side lead): the interactive Reviewer TUI (Textual application mode) and/or the external editor leaves the controlling terminal with ISIG disabled, so Ctrl+C stops GENERATING SIGINT and the guard's handler never fires. CONCRETE MECHANISM (Investigation History #5): Textual's POSIX driver (`textual/drivers/linux_driver.py:338`, `linux_inline_driver.py:267`) explicitly clears ISIG while app mode is active — `ISIG = 0 if os.environ.get("TEXTUAL_ALLOW_SIGNALS") else termios.ISIG; return attrs & ~(termios.ECHO | termios.ICANON | termios.IEXTEN | ISIG)` — and restores a captured `attrs_before` on stop via `tcsetattr` (`linux_driver.py:384`). On macOS (non-win32) Textual selects `LinuxDriver`. Investigation History #6 (PTY probe `spikes/debug/56-textual-isig-probe.py`) NARROWED the leak to a single vector: a CLEAN Textual exit FULLY restores ISIG (`A-CLEAN`: `PRE ISIG=ON` → `POST ISIG=ON` → post-exit ETX `GOT-SIGINT`), so vector (a) "the TUI leaks ISIG on its own clean exit" is REFUTED; but a terminal PRE-corrupted to ISIG-off stays off across a Textual session (`B-PRECORRUPT`: `PRE ISIG=OFF` → `POST ISIG=OFF`, no `GOT-SIGINT`), confirming vector (b) capture-after-corruption. The only TeDDy path that pre-corrupts ISIG is the external-editor suspend cycle: TeDDy's own `_restore_terminal_cooked_mode` re-enables ICANON|ECHO but NOT ISIG (`textual_plan_reviewer_editor.py:205-208`), so an editor (vim/nvim) that exits in raw mode leaves ISIG off and Textual's captured `attrs_before` perpetuate it. Caveat: H2 cannot by itself explain step 7 on a FRESH `start` (planning precedes any TUI, and a clean TUI exit restores ISIG) — it explains "nothing happens" only after the user has opened the editor at least once, or after a prior corrupted session.
  - H2b (CONFIRMED — Investigation History #7): the external-editor suspend cycle is the concrete pre-corruption vector, and TeDDy's own restore is defective. The faithful PTY probe `spikes/debug/56-suspend-isig-probe.py` reproduced TeDDy's EXACT sequence (Textual app mode → `app.suspend()` → an editor that exits in raw mode with ISIG clear → TeDDy's real `_restore_terminal_cooked_mode()` → resume → clean app exit) in a fresh real PTY, then injected a post-exit ETX. Result: `PRE ISIG=ON` → `EDITOR-LEFT-ISIG-OFF` → `AFTER-TEDDY-RESTORE ISIG=OFF` → `APP-EXITED` → `POST ISIG=OFF`, with NO `GOT-SIGINT`. This proves: (a) `_restore_terminal_cooked_mode()` (`textual_plan_reviewer_editor.py:205-208`) re-enables ICANON|ECHO but NOT ISIG, so it does NOT repair the editor's raw-mode corruption; (b) Textual re-captures the (still-corrupted) `attrs_before` on resume, so even a subsequent CLEAN app exit leaves the terminal ISIG-off; (c) once ISIG is off, Ctrl+C no longer GENERATES SIGINT — "nothing happens". This is a definitive TeDDy-side defect, and it explains BOTH verification steps IF the user opened the external editor at least once during the session (the TUI review precedes execution, so step 6 is squarely inside the corrupted window). The FIX is shadow-verified (Investigation History #8): replicating the function with `termios.ISIG | termios.IEXTEN` added restores the terminal's ability to generate SIGINT (`AFTER-TEDDY-RESTORE ISIG=ON` → `POST ISIG=ON` → post-exit ETX `GOT-SIGINT`) — the exact flip from the production probe — empirically proving the one-line fix resolves the defect.
  - H3 (pure environment): the user's terminal/keybinding genuinely does not emit ETX/SIGINT on Ctrl+C. (Still the only remaining explanation for a failure on a TRULY fresh start before any TUI/editor has run — see Discrepancies.) FINAL RESOLUTION: H3 is CONFIRMED for the user's environment — their VS Codium INTEGRATED terminal swallows Ctrl+C before the PTY (IH #14), so NO application-side code fix can recover it there. Independent of the environment, the TeDDy-side defect class (H2b C1 "forgot `ISIG|IEXTEN`" at TWO sites; C2 the console ask-prompt swallow; the console-editor restore asymmetry) is genuine and is formalized for fixing (IH #15; see Solution).

## Solution
### Root cause (two independent, verified findings)

**Finding 1 — Environmental (the user's current symptom; NOT a TeDDy defect).** The user's terminal is the VS Codium **integrated terminal**, which **swallows the Ctrl+C keypress before any program (or the PTY line discipline) sees it**. The decisive byte-level diagnostic (`spikes/debug/56-terminal-input-diagnostic.py`) showed ordinary keystrokes reaching the process (`0x61 0x62 0x63`) while Ctrl+C delivered NEITHER a SIGINT (with `ISIG=ON`) NOR a raw `0x03` (in raw mode); the user's `stty -a` was healthy (`isig` ON, `intr = ^C`). Because the byte never arrives, NO application-side remedy (self-heal ISIG; raw-`0x03` detection) can recover it — the fix is terminal-side (VS Codium keybinding / `terminal.integrated.enableKittyKeyboardProtocol` / copy-on-selection). The user accepted this and will pursue it separately.

**Finding 2 — TeDDy-side defect class (fixes worth landing for HEALTHY terminals).** Independent of the environment, the investigation proved TeDDy contains genuine defects that make Ctrl+C *quiet* even on a perfectly healthy terminal:

- **C1 — "re-enable cooked mode but forget `ISIG|IEXTEN`" (terminal-restore class).** `_restore_terminal_cooked_mode()` (`textual_plan_reviewer_editor.py:207`) and the parallel emergency restore in `SystemEnvironmentAdapter.run_command()` (`system_environment_adapter.py:54`) both re-enable `ICANON | ECHO` but NOT `ISIG | IEXTEN`. After an external editor (vim/nvim) exits in raw mode, these restores fail to repair the terminal, so it stops generating SIGINT and every later Ctrl+C "does nothing" — Shadow-verified end-to-end (IH #8). `console_interactor_helpers.restore_terminal_mode()` (`:39`) is the correct reference pattern (it already ORs `ISIG | IEXTEN`).
- **C2 — "swallow the user's Ctrl+C intent" (failure-transparency class).** `ConsoleAskLoop._pt_prompt` (`console_interactor_ask_loop.py:121`) catches `except (EOFError, KeyboardInterrupt): return ""`, so Ctrl+C at the console ask prompt silently re-prompts instead of exiting (IH #9). The session-loop boundary (`session_cli_handlers.py:340`) already has the correct clean-exit handler a re-raised `KeyboardInterrupt` reaches.
- **Asymmetry — the console ask loop's CLI-editor branch never restores the terminal.** `_launch_editor_background` runs `subprocess.run(editor)` then only `_flush_stdin()`, unlike `_launch_editor_synchronous` (`console_interactor.py:107` → `_restore_terminal()`) and the TUI (three `_restore_terminal_cooked_mode()` sites).

### The proven fix (Shadow-verified, no `src/` edits during investigation)

1. Add `termios.ISIG | termios.IEXTEN` to the two C1 restore sites — Shadow File `spikes/debug/shadow_textual_plan_reviewer_editor.py` flipped the PTY probe from `POST ISIG=OFF`/no-SIGINT to `POST ISIG=ON`/`GOT-SIGINT` (IH #8), proving the fix without touching production code.
2. Restore terminal mode after the console ask loop's CLI editor exits (mirror `restore_terminal_mode()`).
3. Make `_pt_prompt` re-raise `KeyboardInterrupt` (keep swallowing `EOFError`) so Ctrl+C at the console prompt exits cleanly instead of silently re-prompting (the in-session prompt reaches the boundary's clean catch; the pre-boundary INITIAL prompt must be covered by the CLI entrypoint — a verification point for the Developer).

### Systemic preventative measures (the whole class)

- **Single source of truth for the "restore cooked mode" concern (Poka-Yoke).** The concern is duplicated across >=3 files and two of them silently forget `ISIG|IEXTEN`. Consolidate into ONE shared TTY-guarded helper that always sets `ICANON | ECHO | ISIG | IEXTEN | ICRNL`, consumed by the TUI editor, the console interactor, and the system-environment adapter, so a future restore site cannot re-introduce the omission.
- **Failure transparency on Ctrl+C.** Treat `KeyboardInterrupt` as a control signal to propagate, never to swallow; the broad `except (EOFError, KeyboardInterrupt): return ""` masked the user's interrupt (C2). Any "return empty on interrupt" must be an explicit, documented choice scoped to the non-TTY path only.
