# Bug: Trouble Resuming Session Without Explicit Guidance After Container Kill
- **Status:** Resolved
- **Milestone:** TBD
- **Vertical Slice:** TBD
- **Specs:** None

## Symptoms
When a running OpenShell sandbox container executing a TeDDy session is killed mid-run, subsequent `teddy resume` invocations without explicit user guidance (`-m "..."`) sometimes fail to resume work cleanly.

### Expected Behavior
Running `teddy resume` after an ungraceful process or container termination (e.g., `SIGKILL` / container kill mid-action-execution) should detect that the turn had begun executing, record it as interrupted, and hand off to a fresh plan without requiring manual `.teddy/` surgery or mandatory `-m` guidance. A turn killed before any action ran must keep today's behaviour: nothing was applied, so replaying it is safe and a `-m` resume still completes it in place (Bug 60).

### Actual Behavior
As reported by a user running TeDDy inside NVIDIA OpenShell (`teddy-cli==0.2.1` with a local Ollama backend, often in `-y` YOLO mode for long-running sessions), killing a running container leaves the session in a state where `teddy resume` without explicit guidance struggles to continue, leading the user to either pass explicit `-m` guidance or manually roll back turn artifacts in `.teddy/sessions/`.

### Minimal Reproduction Steps (Unverified in Sandbox)
1. Start a multi-turn TeDDy session inside an OpenShell Docker container (e.g., `teddy start -a developer -y` against a local Ollama endpoint).
2. Kill the running OpenShell container mid-turn (during LLM generation, while awaiting input/approval, or mid-execution after one or more actions have already mutated the workspace).
3. Restart/re-enter the container and run `teddy resume` with no `-m` argument.

## Context & Scope
### Regressing Delta
Not a single regression; a structural gap in turn-state persistence and `teddy resume` recovery, observed in `teddy-cli==0.2.1` and still present in current `main`. Verified loci:
- `src/teddy_executor/core/services/session_service.py` (`get_session_state`, `transition_to_next_turn`)
- `src/teddy_executor/core/services/session_repository.py` (`load_meta`)
- `src/teddy_executor/core/services/execution_orchestrator.py` (`execute`, `_process_plan_actions`)
- `src/teddy_executor/core/ports/outbound/session_manager.py` (`SessionState`)
- `src/teddy_executor/adapters/inbound/session_cli_handlers.py` (`_orchestrate_session_loop`, `_handle_startup_error`)

### Environmental Triggers
- Runtime: NVIDIA OpenShell Docker sandbox container (hard container kill / ungraceful `SIGKILL` bypassing `KeyboardInterrupt`, `finally` cleanup, and the two-phase interrupt drain).
- LLM backend: Slow local Ollama endpoint (e.g., `qwen3.8:27b` with long timeout), increasing the window during which a container may be killed mid-turn.
- Invocation mode: Interactive or `-y` (YOLO) multi-turn loop via `teddy start` / `teddy resume` without `-m`.

### Ruled Out
- **Silent `pathfinder` fallback on a missing `meta.yaml`.** Ruled out: `LocalFileSystemAdapter.read_file` re-raises `FileNotFoundError` for a missing file; an existing but empty `meta.yaml` is the only case that degrades to `{}`. `get_cumulative_cost` -> `load_meta` -> `read_file` runs before dispatch in `_orchestrate_session_loop`, so a missing `meta.yaml` surfaces as `Error: [Errno 2] ...` and exit 1 via `_handle_startup_error`, not a silent fallback.
- **The `--pipeline` MESSAGE-stop as the primary path.** Ruled out: `awaiting_reply` is set only on that one path, but the reported symptom is a long-window action-execution interruption, not a pipeline stop.
- **`ActionStatus.INTERRUPTED` already covering recovery.** Ruled out for hard kills: the status exists and is consumed (`execution_report.py:27`, set at `action_dispatcher.py:103`, folded into run status at `execution_report_assembler.py:55-59`), but it lives in the in-memory `ActionLog` and reaches disk only via `report.md` at `finalize_turn`. It fully covers a graceful interrupt, which finalizes normally. It cannot cover a hard kill, which runs no code.
- **Clearing pre-flight by hydration alone.** Ruled out: `PlanValidator.validate` iterates every action unconditionally, so even with completed actions marked `executed`, pre-flight would still reject an already-applied `CREATE`.
- **Treating every `PENDING_PLAN` turn as interrupted.** Ruled out by explicit product decision: a completely pending turn — no action executed — keeps today's behaviour, including Bug 60's in-place `-m` completion of the pending plan. Recovery therefore needs positive evidence that execution began, which is why the fix adds a durable marker instead of inferring from turn classification.

## Diagnostic Analysis
### Causal Model
Verified by MRE-01 (`spikes/debug/resume-after-container-kill/01-pending-plan-bare-resume-mre.py`), MRE-02 (`02-replayed-plan-rejected-preflight-mre.py`), and source inspection. An abrupt container kill leaves only durable on-disk writes that completed before the kill; no `finally`, abort handler, or interrupt drain runs.

1. **Turn classification is presence-only.** `SessionService.get_session_state` returns `COMPLETE_TURN` if `report.md` exists, `PENDING_PLAN` if only `plan.md` exists, else `EMPTY`. It carries no record of partial execution.

2. **No per-action progress is persisted.** `ExecutionOrchestrator._process_plan_actions` dispatches actions and accumulates `ActionLog`s in memory only. The `ExecutionReport` is assembled after every action finishes, and `report.md` is written by `finalize_turn`. A hard kill during action execution therefore leaves `plan.md` with no `report.md` and no execution history: `PENDING_PLAN`.

   The interrupt statuses do not change this. `ActionStatus.INTERRUPTED` is set by `ActionDispatcher` (`action_dispatcher.py:103`), the two-phase Ctrl+C drain skips the remaining actions with `INTERRUPT_REASON` (`execution_orchestrator.py:88-89`), and `ExecutionReportAssembler` folds `ActionStatus.INTERRUPTED` into `RunStatus.INTERRUPTED` (`execution_report_assembler.py:55-59`). Every one of those values lives inside the in-memory `ActionLog`; they reach disk only through `report.md` at `finalize_turn`. A graceful `q`/`Ctrl+C` therefore finalizes a `COMPLETE_TURN` whose report carries the interrupt statuses, and resume proceeds to the next turn. A SIGKILL or container kill runs none of that code, so the statuses are never computed and never persist.

3. **Bare resume replays from action 1.** With `message=None`, `_parse_pending_plan` returns `None`; `_should_consume_awaiting_reply` is `False` unless the `awaiting_reply` flag was set; the final branch calls `SessionOrchestrator.execute(plan_path=...)`. MRE-01 shows exactly one `execute(plan_path=...)` call, no pre-parsed plan, and no progress record.

4. **The replay is rejected in pre-flight.** The re-parsed plan is validated against the mutated workspace. An already-applied `CREATE` target now exists, so `CreateActionValidator` returns `File already exists: ...` (MRE-02). `ExecutionOrchestrator.execute` raises `InvalidPlanError`; in session mode `SessionOrchestrator` funnels the validation failure into `trigger_replan`, producing a fresh LLM plan against an already-mutated workspace. That is the "struggles to continue" symptom; the user then passes `-m` or rolls back `.teddy/` turn artifacts.

5. **Mid-transition gap is graceful but unrecoverable (secondary).** `transition_to_next_turn` writes the next turn directory, then `meta.yaml`, then `turn.context` as three separate calls. A kill between them leaves a turn directory without `meta.yaml`; `read_file` re-raises `FileNotFoundError`, and resume aborts with `Error: [Errno 2] ...` and exit 1 (see Ruled Out). The window is the three-write span.

6. **Unflagged `## Message` turn (secondary).** A `## Message` plan written but not finalized is `PENDING_PLAN` without `awaiting_reply`. Bare resume does not recognise it as an awaiting reply; it re-dispatches the plan. A MESSAGE-only plan bypasses review (`is_communication_turn`) and re-dispatches the MESSAGE action instead of collecting the user's reply.

7. **"Execution had begun" is not recorded anywhere.** `get_session_state` (`session_service.py:198-217`) reads only `plan.md` and `report.md` presence, so a never-dispatched turn and a killed-mid-execution turn are indistinguishable on disk. Any fix that must treat them differently needs a durable write that survives a hard kill. The chosen marker is a turn-scoped file; `transition_to_next_turn` (`session_service.py:246-304`) creates the next directory, persists `meta.yaml`, and writes `turn.context`, copying no files, so a marker cannot leak into a later turn.

### Discrepancies
- [x] `SessionService.get_session_state` infers turn state purely from `plan.md` / `report.md` presence and cannot detect partial or in-flight execution. (Resolved: verified by inspection. This is the classification substrate of the failure, not a defect in isolation.)
- [x] `SessionLifecycleManager._parse_pending_plan` short-circuits to `None` when `message` is absent, so a `PENDING_PLAN` turn is never recognised as an unflagged `## Message` turn on bare resume. (Resolved: verified; the `awaiting_reply` flag is the only recognition path and is set solely for `--pipeline` MESSAGE stops.)
- [x] A partially executed `PENDING_PLAN` turn has no incremental action-outcome journal before `finalize_turn`, so bare resume re-executes already-applied actions; the replay is rejected in pre-flight (`File already exists`) and funnels into `trigger_replan` against a mutated workspace. (Resolved: verified by MRE-01 and MRE-02. Primary root cause.)
- [x] `transition_to_next_turn` writes turn dir, `meta.yaml`, and `turn.context` non-atomically. (Resolved: verified. Corrected from the original claim — a missing `meta.yaml` raises `FileNotFoundError`, which surfaces as `Error: ...` exit 1 via `_handle_startup_error`, not a silent fallback to `pathfinder`.)
- [x] The recovery design appeared to contradict a pinned contract: Bug 60 deliberately made a `-m` resume seed and execute the pending plan in place, and `test_pipeline_message_and_resume_flow.py:384-419` asserts it end to end. (Resolved: no conflict remains under the marker-gated design. A never-dispatched turn carries no marker, so it keeps Bug 60's in-place completion byte for byte; only a turn that had begun executing is recovered. The earlier "retire the contract" verdict is withdrawn.)
- [x] `get_session_state` cannot distinguish a never-dispatched `PENDING_PLAN` turn from a mid-execution kill, so "execution had begun" is unobservable from what the state machine reads. (Resolved: add one durable turn-scoped marker (`execution.started`) written by `ExecutionOrchestrator.execute` immediately before the first dispatch, guarded on `plan.is_session`. `transition_to_next_turn` copies no files into the next turn, so the marker cannot leak forward.)

## Solution
### Root Cause
Verified. Bare `teddy resume` cannot continue an interrupted `PENDING_PLAN` turn because TeDDy persists no per-action execution progress. A graceful `q`/`Ctrl+C` is already handled: the drain marks the remaining actions `SKIPPED` with `INTERRUPT_REASON`, `finalize_turn` writes `report.md` carrying those statuses, and resume moves to the next turn. The gap is exclusively the hard kill (SIGKILL / container kill), which runs no Python: no drain, no `INTERRUPTED`/`SKIPPED` computation, no `report.md`. Only `plan.md` survives, with no record of completed actions. Bare resume therefore replays `plan.md` from action 1 (MRE-01), and pre-flight rejects the actions the killed run already applied (MRE-02), which in session mode triggers an automated replan against an already-mutated workspace. Secondary modes are a narrow non-atomic next-turn transition (`Error: ...`, exit 1) and unflagged `## Message` turns, which are re-dispatched instead of collecting a reply.

The chosen fix recovers only a turn that had already begun executing. A completely pending turn is untouched: nothing was applied, so replaying it is safe and Bug 60 keeps its in-place `-m` completion. But turn classification reads only `plan.md`/`report.md` presence (`session_service.py:198-217`), so "execution had begun" is not observable today. The fix therefore adds one durable turn-scoped marker and gates recovery on it. `ExecutionOrchestrator.execute` writes `{turn_dir}/execution.started` after pre-flight validation succeeds and after the review-abort branch, immediately before the first dispatch, guarded on `plan.is_session`. On resume, a `PENDING_PLAN` turn that carries the marker is recovered the way a gracefully interrupted turn already is: synthesize a report whose actions are `INTERRUPTED` with an explicit "outcome not recorded" note, `finalize_turn` it (writes `report.md`, creates the next turn), carry the `-m` reply as `## User Request`, then plan the NEXT turn from scratch against the observed workspace via `_handle_planning_and_execution`. This reuses compositions the codebase already ships: `_synthesize_message_report` builds a report from a parsed plan at resume time, `trigger_replan` already finalizes-then-plans, and `_consume_awaiting_reply` already synthesizes-finalizes-preserves. No new port is needed because production already injects `plan_parser`, `time_service`, and `report_assembler` into `SessionPorts` (`container.py:367-369`), and the orchestrator already holds `file_system_manager`. It abandons the interrupted plan's remainder and lets the fresh plan observe the mutated workspace, which is safer than replaying non-idempotent `EXECUTE` actions. An unparseable or absent marker falls through to today's `execute → InvalidPlanError → trigger_replan` path, and a pure `MESSAGE` (communication) turn keeps today's re-execute path because re-running the message re-collects the reply. The recovery chain is proven by MRE-04 (`spikes/debug/resume-after-container-kill/04-finalize-as-interrupted-recovery-proof.py`); the marker itself is proven only by inspection and is NOT yet applied to `src/`.

### Affected Components

Scope boundary (product decision): a completely pending turn — no action executed — keeps today's behaviour exactly, including Bug 60's in-place `-m` completion. Only a turn that had begun executing is recovered as INTERRUPTED. This is why the fix needs a marker: without one, `get_session_state` cannot tell the two apart.

Required ordering inside `resume`: terminate-on-empty-reply, the flagged `awaiting_reply` short-circuit, and the blank-message prompt stay **ahead** of the gate (`test_empty_reply_terminates_without_execution`, `test_flagged_turn_prompts_for_the_reply_only`, `test_prompts_and_seeds_the_pending_plan`), and the `InvalidPlanError → execute → trigger_replan` fallback stays **behind** it.

**Chosen fix — marker-gated INTERRUPTED recovery:**
- **`ExecutionOrchestrator.execute` (marker write)**: after `self._plan_validator.validate` succeeds (`execution_orchestrator.py:305`) and after the review-abort branch (`:319-320`), immediately before `_process_plan_actions` (`:322`), write an empty `{Path(plan_path).parent}/execution.started` through the already-injected `self._file_system_manager` (`__init__` at `:24-35` binds `ports.file_system_manager`). Guard on `reviewed_plan.is_session` so stateless `--plan-content` execution never writes it. A pre-flight rejection and an aborted review execute nothing and therefore carry no marker.
- **`SessionLifecycleManager.resume` (`PENDING_PLAN` branch)**: after the awaiting-reply consume returns (`:100-110`) and before the seed-and-dispatch (`:111`), read the marker; when present and the plan is not a communication turn, take the recovery branch. On a bare resume `_parse_pending_plan` returns `None`, so parse via `_parse_awaiting_plan(turn_path, plan_path)` (`:441-465`); an `InvalidPlanError` there falls through to today's `execute → InvalidPlanError → trigger_replan` funnel rather than being swallowed.
- **`SessionLifecycleManager._recover_interrupted_turn` (new helper)**: synthesize the report, `finalize_turn(plan_path, report, plan=plan)`, then `_handle_planning_and_execution(next_turn_dir, ..., message=message)` — the same tail shape `_consume_awaiting_reply` already uses (`:426-439`), including the preservation decision that `finalize_turn` performs from the report's `## User Request`.
- **`SessionLifecycleManager._synthesize_interrupted_report` (new helper)**: sibling to `_synthesize_message_report` (`:466`); one `ActionLog` per plan action with `ActionStatus.INTERRUPTED` and an "outcome not recorded" `details` note, passing the reply through `ReportAssemblyData(message=...)` so the report carries `## User Request` (rendered by `execution_report.md.j2:322-325`, which `_is_preserved_turn` at `session_service.py:330-350` promotes into prune-exempt `session.context`).
- **Reused unchanged**: `finalize_turn` (`:643`), `transition_to_next_turn`, `_parse_awaiting_plan`, `_handle_planning_and_execution` (`:527-609`), `ExecutionReportAssembler`. `transition_to_next_turn`'s three-write non-atomicity (`session_service.py:246-302`) stays an independent hardening item.

#### Rejected Alternative: per-action journal (MRE-03)
MRE-03 proves a durable journal works, but it needs a new persistence port (plus every fake and two port-contract tests), write-side instrumentation in `ExecutionOrchestrator`, executed-aware pre-flight on both the stateless and session paths, and a replan guard — a far larger surface than the recovery routine, for the same user outcome. Kept below as a deferred alternative in case in-place completion of the interrupted plan is ever required.

- **`ISessionRepository` / `ISessionManager` / `SessionRepository` / `SessionService`**: add per-turn action-journal read/write next to the existing `load_meta`/`save_meta` (`session_repository.py`) and `load_turn_meta`/`save_turn_meta` (`session_service.py`). `ISessionManager` is a `Protocol`; every implementer (`SessionService`) and every in-memory fake must gain the method. Contract pins: `tests/suites/unit/core/ports/test_session_manager_contract.py` and `.../test_session_repository_contract.py`. 18 test files reference `ISessionRepository` (resume/meta CLI tests, `test_session_service*`).
- **`SessionService.transition_to_next_turn`** (`session_service.py:246-302`): make the turn-dir (`:266`) -> `meta.yaml` -> `turn.context` (`:302`) sequence atomic — persist `meta.yaml` before the directory is advertised as latest, or build in a temp dir and rename. Independent of journaling.
- **`ExecutionOrchestrator`** (`execution_orchestrator.py`): write each action's outcome to the journal atomically after `_dispatch_single_action`, at the `_handle_action_in_loop` boundary (`:128-172`) where `action_log`/`should_halt` already exist. Inject the journal writer via `OrchestratorPorts` (constructor injection). The replay-skip path is the existing `executed`/`action_log` branch at `:137`.
- **`PlanValidator.validate` / `ExecutionOrchestrator.execute`**: `PlanValidator` has no executed-awareness and iterates every action. Either filter journaled actions before `self._plan_validator.validate(plan)` (`execution_orchestrator.py:305`) or make the validator skip journaled targets. The session path also validates in `SessionOrchestrator._validate_plan_with_context` (`session_orchestrator.py:607`), so the filter must apply there too.
- **`SessionLifecycleManager.resume`** (`session_lifecycle_manager.py:59`): the `PENDING_PLAN` branch (`:78`) dispatches `execute(plan_path=...)`; hydrate the journal into the re-parsed plan there, or let the orchestrator hydrate from `plan_path` before pre-flight (`_parse_pending_plan` at `:231`). `PENDING_PLAN` consumers: `session_manager.py:12`, `session_lifecycle_manager.py:78`, `session_orchestrator.py:443`, `session_service.py:215`.
- **`SessionOrchestrator` replan funnel** (`:607` -> `_handle_logical_validation_errors` -> `trigger_replan`): a genuine journaled replay whose remaining actions validate clean must not fall through to replan.
- **Pre-executed-path tests** (`test_execution_orchestrator.py`, `test_models.py`, `test_tui_label_formatting.py`, `test_reviewer_app_core.py`) pin the `executed`/`action_log` skip and must stay green.
