# Bug: Turn Metadata Telemetry Stalls After the Turn Header Prints
- **Status:** Resolved
- **Milestone:** N/A
- **Vertical Slice:** N/A
- **Specs:** N/A

## Symptoms
In an interactive session the turn header prints immediately, for example `[08] session-slug | Waiting for Pathfinder to respond...`. The telemetry block that shows Model, Context usage, and Session Cost arrives only after a perceptible stall. The user reports that the stall is far worse on Windows 11 than on macOS, where the same session feels responsive. Expected behavior is that the telemetry block prints within a few hundred milliseconds of the header.

Minimal reproduction steps:
1. Start an interactive session with a model that is not pre-registered in the LiteLLM cost map, for example an OpenRouter routed model.
2. Send a message and wait for the turn header and the telemetry block.
3. Observe the gap between the header line and the Model, Context, and Session Cost lines.

## Context & Scope
### Regressing Delta
Not a regression. The cost is inherent to the original two-pass design of `local_repo_tree_generator.py`, which walks the repository into a path set and then formats that set with a second filesystem pass. The stall lives between the header print at the top of `PlanningService.generate_plan` and `PlanningService._display_telemetry` near the end of the same method.

### Environmental Triggers
- Windows 11 host with `cmd.exe`.
- Interactive session, where the header prints before context assembly and token counting.
### Ruled Out
- The pytest-httpserver loopback stall from case file 45: the metadata path performs no loopback HTTP request.
- A cold LiteLLM import as a recurring cost: warm `validate_environment` and `validate_config` cost 0.000-0.001s, so the 2.5s reading was the one-time import that only a cold process pays.
- A first-use tiktoken encoding download: the BPE cache file exists at 2.15 days old and warm `token_counter` costs 0.035s.
- OpenRouter registry hydration: the persistent cache is fresh at 2.078 days, and both `get_context_window` calls cost at most 0.006s.

## Diagnostic Analysis
### Causal Model
Verified model: the stall is warm per-turn filesystem and process work between the header print and the telemetry block. The header prints first. `ContextService.get_context` then assembles the payload with a repository tree walk and a `git status` shell-out. The client then counts the assembled messages, and the telemetry block prints last. The warm window costs about 0.31s on this host. The repository tree walk costs 0.159-0.165s and the git shell-out 0.038s. The Windows penalty is the per-entry walk cost from `Path` construction, `relative_to`, and pathspec matching. The cold-import, encoding, hydration, console, and payload-write candidates were measured and excluded as recurring costs. The candidates, in execution order, are:
1. `_run_preflight_check` calls `validate_config`, which lazily imports `litellm` on first use. (Measured: the import costs 2.629s once, and warm validation costs 0.000-0.001s, so this is not recurring.)
2. `get_text_token_count(system_prompt, model)` lazily imports `tiktoken` and resolves an encoding on first use. (Measured: warm tokenization costs 0.003-0.035s, and the encoding cache is fresh, so this is not recurring.)
3. `ContextService.get_context` assembles the payload, including a `git status` shell-out and a repository tree walk. (Measured as the dominant recurring cost.)
4. `get_context_window(model)` triggers OpenRouter registry hydration when the model is absent from `litellm.model_cost`. (Measured: the persistent cache is fresh and each call costs at most 0.006s, so hydration is not recurring.)
5. `litellm.token_counter` counts the assembled messages. (Measured: the message token count costs 0.048s.)

Verified wiring facts: the hydrator is a container singleton with the persistent cache path `.teddy/.model_registry_cache.json` and a config-driven TTL (`llm.registry_cache_ttl_days`, default 7 days). That cache file exists at 845,124 bytes, aged 2.078 days, and holds 471 models. `get_context_window` runs up to three times per turn, once for pre-emptive hydration, once in `_display_telemetry`, and once in `_check_context_budget`. `_fetch_models` leaves `_cached_models` unset when the network fetch fails, so a stale or absent cache can turn each of those calls into a fresh 10-second request. The class-level `_PREFLIGHT_DONE` flag is written by `_run_preflight_check` but never read, so `validate_config` runs on every turn.

Verified payload growth: the live session carries six turns, and its context payload grows from 100,647 bytes at turn 01 to 241,761 bytes at turn 06, reaching 59,121 tokens. The served model is `openrouter/~deepseek/deepseek-flash-latest:nitro`, and its actual model is `deepseek/deepseek-v4.1-flash-1017`. Every token-counting and hydration call scales with this payload.

Verified phase timing (fresh probe process): the header-to-telemetry window costs about 3.1s total. `validate_config` dominates at 2.501s, but that reading includes the one-time LiteLLM import because the probe process was cold. `get_context` costs 0.384s, `repo_tree` 0.156s, `git_status` 0.039s, `get_token_count` 0.045s, and the first `get_context_window` 0.006s. The tokenizer is fast (0.035s warm) and its BPE cache exists at 2.15 days old, so neither tokenization nor hydration explains a multi-second stall. The served and actual model IDs are both unregistered in `litellm.model_cost`.

Verified warm attribution (probe 03): the one-time LiteLLM import costs 2.629s, while every later `validate_environment` and fresh-adapter `validate_config` call returns in 0.000-0.001s. The 2.501s phase reading was therefore the import, and a live session reuses the imported module after its first turn. Warm context work dominates the measured window: `repo_tree` costs 0.156-0.158s per call, `git_status` 0.037-0.040s per call, and `get_context` 0.395s then 0.257s, which includes both the tree walk and the git shell-out. The remaining per-turn candidates are the context file reads and the repeated token counting, not validation, hydration, or encoding setup.

Verified aggregate window (probe 04): the full warm header-to-telemetry sequence costs 0.906s on its first run and 0.602s on its second run. The second run is the steady-state figure. Its timed phases sum to 0.518s, and the untimed remainder is `create_container()` near 0.08s, which a live session pays once per process. The real per-turn sequence is therefore about 0.31s: `get_context` 0.259s, message token count 0.048s, system prompt token count 0.003s, and validation, path resolution, prompt fetch, hydration, and pricing all at or below 3ms. The `include_tokens` A/B measured 0.206s without per-file tokenization against 0.259s with it, so tokenization contributes about 49ms and context reads plus the tree walk and git shell-out contribute the rest.

Verified suite startup cost (probe 05): collection costs 2.86s serially and 2.70s under twelve xdist workers for 1874 tests. Collection is therefore not multiplied per worker, so fixed worker startup cannot produce a two-fold suite gap.

Verified console and payload write cost (probe 05): the four Rich writes that render the header and the three telemetry lines cost 0.016s on their first run and 0.001s on later runs. A 325KB `input.md` write costs 0.001s. The console is constructed once and cached on the interactor, so terminal rendering contributes nothing to the stall.

Verified cost decomposition: `get_context` costs 0.259s with per-file tokenization and 0.206s without it. The repository tree walk costs 0.156s and the git shell-out 0.038s, so those two filesystem and process operations account for about 94% of context assembly. File reads and string formatting account for roughly 12ms. The stall is therefore dominated by the tree walk and the git status shell-out, which are the Windows-sensitive primitives that case file 45 already quantified.

Verified traversal measurement (probe 06): the real generator costs 0.159-0.165s and emits 1,077 lines over 25,222 characters. A raw traversal that descends everywhere visits 33,715 entries and costs 0.415s, while a raw traversal that prunes the standard ignored directory names visits 897 entries and costs 0.010s.

Implementation facts from reading the generator (supersedes probe 06's "descends then discards" wording): `walk_recursive` evaluates `spec.match_file(match_path)` and calls `continue` before it yields a directory and before it recurses, so ignored directories are pruned during descent rather than visited and discarded. `load_ignore_spec` seeds a fixed default set `{.git/, .venv/, __pycache__/, .teddy/, .ruff_cache/}` and augments it with the literal `.gitignore` and `.teddyignore` pattern lines. `_RecursiveListFormatter.format` re-stats every included path with `p.is_dir()` and `p.is_symlink()` while sorting its directory list, then calls `directory.iterdir()` once per directory and filters the result against the included set. The performance test `test_tree_generator_performance` only guards a 500-file ignored `.venv` against a 50ms budget and is skipped on GitHub Actions.

Verified walk-and-formatter attribution (probe 07): the real walk yields only 896 entries across 92 directories, so ignored directories are genuinely pruned and no large un-ignored directory is traversed. The top-level pruned directories are `.git`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.teddy`, and `.venv`, so a project ignore file names the two cache directories that the fixed default set omits. The generator's 0.157s decomposes into `_get_included_paths` at 0.129s and the full formatter at 0.028s, split into 0.011s for the directory stat-and-sort pass and 0.012s for the per-directory `iterdir` scans. The formatter is therefore not the cost. Inside `_get_included_paths`, `walk_recursive` alone costs 0.109s for those 896 entries, which is roughly 120µs per entry against 11µs for the plain pruned `os.walk` that probe 06 measured at 0.010s. The per-entry work inside `walk_recursive` is the remaining cost, and probe 08 must split it between the two `os.path` stat syscalls, the `Path` and `relative_to` construction, and the pathspec match.

Verified per-entry decomposition (probe 08): the production walk costs 0.1089s for 897 entries. The instrumented walk attributes 0.0455s to `Path` construction plus `relative_to`, 0.0319s to `spec.match_file`, 0.0100s to `os.path.isdir`, 0.0056s to `os.path.islink`, and 0.0224s to scandir, recursion, and set work. The `Path` and `relative_to` construction is therefore the largest single component, and the two stat syscalls together account for only 0.0156s. A replica that replaces the two stat syscalls with `DirEntry.is_dir(follow_symlinks=False)` and `is_symlink()` yields the identical 897 paths and identical directory flags but costs 0.0966s, only 11% less than production. The cached-stat fix alone is therefore insufficient, and the candidate fix must also thread relative path strings through the recursion to remove the per-entry `relative_to` call and fuse the walk with the formatter to remove the second filesystem pass.

Verified fused formatter (probe 09): both candidate variants reproduced the production output byte for byte on the real repository (1,080 lines) and on a synthetic tree (19 lines). The dict-formatter variant, which keeps the production walk and formats from a path-to-is_dir map, cost 0.1468s against the production 0.1939s. The fused variant, which threads relative strings, reads the directory flag from the scan cache, and builds each section during the same pass, cost 0.0429-0.0431s, about 4.5 times faster than production. The caller census shows `walk_recursive` is also used by `local_file_system_adapter.py`, so the fused rewrite stays inside `local_repo_tree_generator.py` and leaves the shared helper untouched. The fused implementation must key the root section with `.` to match production, because production sorts every directory by `str(relative_to(root)).lower()` and the root resolves to `.`. Directories named with a leading character below `.`, such as `!important` or `#hash`, therefore render their sections before the root block. The replica reproduced the production output on the real repository but printed the root block first on the synthetic tree, which is the only observed deviation.

Verified replica and shipped fix (probe 10): the corrected replica reproduced the production output byte for byte on the real repository (1,082 lines, 0.0392s against 0.1596s) and on the adversarial synthetic tree (37 lines, 0.0007s against 0.0045s). The same single-pass traversal now ships in `local_repo_tree_generator.py`, and the permanent ordering test pins the `.` root key. The walk therefore drops from about 0.160s to about 0.039s. The remaining recurring costs are the git shell-out at 0.038s, the message token count at 0.048s, and per-file tokenization at 0.049s, so the residual window is about 0.19s by arithmetic over measured parts. The full suite is green at 1,839 passed and 36 skipped in 30.78s.

### Discrepancies
- [x] The telemetry block appears after a stall on every turn, while the cold-import candidates apply only to the first turn of a process. (Resolved: a warm `validate_config` costs 0.000s and the 2.5s reading was the one-time import, so the recurring cost must be per-turn context assembly and token counting.)
- [x] The stall is reported as much worse on Windows 11 than on macOS. (Resolved: the window is dominated by the repository tree walk at 0.156s and the git shell-out at 0.038s. Every other phase is at or below 3ms and is identical across platforms. The platform difference is therefore filesystem traversal and process spawn, the same Windows penalty that case file 45 measured at 40ms per `git status` and 11-42ms per process spawn.)
- [x] The two `os.path` stat syscalls dominate the walk. (Resolved: they cost only 0.0156s together, and the `DirEntry` replica saved 11%. The `Path` construction plus `relative_to` dominates at 0.0455s.)
- [x] The fused replica reproduces production on the real repository but not on the synthetic tree. (Resolved: production keys the root section with `.`, so directories named below `.` render before the root block, and the replica used an empty-string key instead. The replica now reuses the `.` key and matches byte for byte on both trees.)
- [x] The fused rewrite could orphan the shared walk helper. (Resolved: `walk_recursive` still serves `local_file_system_adapter.py`, so the fix stays inside `local_repo_tree_generator.py` and reuses only `load_ignore_spec`.)

## Solution
### Root Cause
The stall is warm per-turn filesystem work between the turn header and the telemetry block. `ContextService.get_context` asked `LocalRepoTreeGenerator` for the repository tree on every turn. The generator walked the repository into a `set[Path]` and then formatted that set with a second filesystem pass. Each of about 900 included entries paid a `Path` construction plus `relative_to` (0.0455s total), a pathspec match (0.0319s), and two `os.path` stat calls (0.0156s). The walk alone cost 0.109s of the 0.157s generator cost, and the formatter cost 0.028s. The fix was proven in the sandbox replica on the real repository and on an adversarial synthetic tree, then applied directly to `src/`.

The shipped fix renders the tree in a single filesystem pass. It threads relative path strings through the recursion, reads the directory flag from the `os.scandir` entry cache, and builds each section during that same scan. The walk drops from about 0.160s to about 0.039s, roughly four times faster. The git shell-out at 0.038s, the message token count at 0.048s, and per-file tokenization at 0.049s remain, so the residual window is about 0.19s by arithmetic over measured parts, down from about 0.31s.

### Affected Components
- `local_repo_tree_generator.py`: now owns a single-pass traversal, reuses only `load_ignore_spec` from `filesystem_helpers`, and renders each section during the scan.
- `test_local_repo_tree_generator.py`: adds `test_repo_tree_generator_orders_sections_by_relative_path`, which pins the `.` root key ordering against a top-level directory named `!important`.
- `filesystem_helpers.py`: unchanged. `walk_recursive` still serves `local_file_system_adapter.py`, so the shared helper stays untouched.
- `local_repo_tree_generator.md`: describes the single-pass traversal, the narrowed helper dependency, and the `single_pass_traversal`, `scan_cache_flags`, and `section_order` invariants.
