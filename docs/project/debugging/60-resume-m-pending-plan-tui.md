# Bug: `resume -m` on a PENDING_PLAN Turn (plan.md, no report.md)

- **Status:** Resolved
- **Milestone:** N/A (ad-hoc)
- **Vertical Slice:** [00-21-session-interrupt-resume-message.md](/docs/project/slices/00-21-session-interrupt-resume-message.md)
- **Specs:** [interactive-session-workflow.md](/docs/project/specs/interactive-session-workflow.md)

## Symptoms

**Expected:** On a session whose latest turn has `plan.md` present but no `report.md` (a `PENDING_PLAN` turn), running `teddy resume -m "<message>"` should:
- **Auto-approve (`-y`)**: execute the pending plan AND append the supplied message as a user request, so the injected instruction is honoured.
- **Interactive (no `-y`)**: open the plan-review TUI with the supplied message already loaded as the pending message — as if the user had pressed `m` in the TUI and typed the message — so opening the message temp file shows the message verbatim; any subsequent edit is harvested and overrides the initial `-m` value.

**Actual (confirmed by MRE, `spikes/debug/60-resume-m-pending-plan-mre.py`):** the injected `-m` message is DROPPED: the pending non-communication plan is re-executed with no `message`/seed, no `## User Request` section is rendered, and the message is not seeded into the plan-review TUI buffer.

**Steps:**
1. Leave a session whose latest turn has `plan.md` present and `report.md` absent (PENDING_PLAN).
2. Run `teddy resume -m "next instruction"` (with and without `-y`).
3. Observe the message is dropped.

## Context & Scope

### Regressing Delta
Not a single regressing commit; this is a GAP recorded in PROJECT.md Technical Debt ("Non-communication `PENDING_PLAN` turns drop an injected `resume -m` reply — the `PENDING_PLAN` non-awaiting branch calls `orchestrator.execute(...)` WITHOUT forwarding `message`"). Bug 57 ([57-resume-message-interactive-no-pipeline.md](/docs/project/debugging/57-resume-message-interactive-no-pipeline.md)) fixed only the COMMUNICATION (single-MESSAGE) turn case, narrowing the consumption guard to `message and self._is_communication_turn(turn_path)`; the NON-communication branch was deliberately left forwarding no message.

### Environmental Triggers
Session in `PENDING_PLAN` state (`SessionService.get_session_state`: plan.md exists AND report.md absent) + `resume -m`. The auto-approve vs interactive split depends on how the `resume` command maps `-y`/config into the plan-review path (to be verified).

### Ruled Out
- The awaiting-reply consumption path (`_consume_awaiting_reply`) — Bug 57 verified it CONSUMES the reply; this turn is NOT `awaiting_reply` and NOT a communication turn, so that path is not the site.

## Diagnostic Analysis

### Causal Model
`SessionLifecycleManager.resume` (verified at HEAD) handles `PENDING_PLAN` with two disjoint branches:

```python
state, turn_path = self._session_service.get_session_state(session_name)
if state == SessionState.PENDING_PLAN:
    turn_meta = self._session_service.load_turn_meta(turn_path)
    if turn_meta.get("awaiting_reply") or (
        message and self._is_communication_turn(turn_path)
    ):
        return self._consume_awaiting_reply(...)   # consumes the reply
    plan_path = f"{turn_path}/plan.md"
    report = orchestrator.execute(                 # <-- `message` NOT forwarded
        plan_path=plan_path,
        interactive=interactive,
        project_context=project_context,
        pipeline=pipeline,
    )
    return (session_name, report)
```

For a NON-communication `PENDING_PLAN` turn, the injected `message` is never passed to `orchestrator.execute` (nor appended to any report, nor seeded into the review TUI): the pending plan is re-executed and the message is lost. This is the ONLY dispatch site that discards `message`.

**Desired behavior (from the user report).** On a `PENDING_PLAN` turn, `resume -m "<msg>"` must HONOR the message in BOTH modes — under `-y` (`interactive=False`) execute the pending plan with the message as the report's user request; under interactive open the plan-review TUI with the message pre-loaded as the pending message (pressing `m` shows it; an edit harvests and overrides). **Fix (VERIFIED via shadow file, Turn 8; path-precision correction Turn 13).** In the non-communication branch, when `message` is supplied: parse the pending plan WITH its path (extend `_parse_awaiting_plan(turn_path)` to forward `plan_path=plan_path`, or inline `self._plan_parser.parse(content, plan_path=plan_path)`), seed `plan.metadata["user_request"] = message`, and call `orchestrator.execute(plan=plan, plan_path=plan_path, interactive=..., project_context=..., pipeline=...)` WITHOUT `message=` (passing `message` would win in the assembler and defeat TUI-harvest override). The communication-turn route (Bug 57 `_consume_awaiting_reply`) is unchanged. Empirical proof (shadow MRE, rc=0): `{'interactive=False': True, 'interactive=True': True, 'no_message_reexecutes': True}`. NOTE: the path-LESS shadow edit proved the message-seeding CONTRACT but would drop `Plan.is_session`/`Plan.plan_path` in production (since `execute(plan=..., plan_path=...)` short-circuits `_resolve_plan`), so the shipped fix MUST parse with the path.

### Discrepancies
- The user expects an auto-approve (`-y`) vs interactive split in which the message is honoured in BOTH modes; at HEAD the message is honoured in NEITHER for a non-communication `PENDING_PLAN` turn. Unresolved.
- RESOLVED (reading): `resume` exposes `-y/--yolo`; `interactive = not (yolo or pipeline or yes or ...)`. Under `-y`, `orchestrator.execute(interactive=False)` runs with no TUI; the message is simply dropped (not forwarded). Under interactive, `orchestrator.execute(interactive=True)` DOES open the TUI (`_perform_interactive_review`), but without the message seeded.
- RESOLVED (reading): `ExecutionOrchestrator.execute(message=...)` reaches ONLY report finalization/abort — it is never passed to `_perform_interactive_review`/`review()`. So the interactive-seed facet needs an explicit seed (candidate: set `plan.metadata["user_request"]` before review, or extend the `review` signature).
- RESOLVED (reading): the report's user request is `user_request = data.message or data.plan.metadata.get("user_request")` (`execution_report_assembler.py:38`). EITHER forwarding `message` OR seeding `plan.metadata["user_request"]` makes the report carry `- **User Request:** <message>`. CAVEAT: when BOTH are set, `data.message` WINS — so passing `message` would OVERRIDE a TUI harvest. The correct seed therefore sets `plan.metadata["user_request"]` and does NOT pass `message`.
- RESOLVED (reading): seeding `plan.metadata["user_request"]` before execution pre-loads the TUI `m` editor (the handler seeds from `plan.metadata["user_request"]` when `_user_message_cache` is None) and survives confirmation when the user never presses `m` (`_finalize_user_message` returns early on `msg is None`, leaving the seed intact); if the user presses `m` and edits, the harvest overwrites `plan.metadata["user_request"]`, which then WINS in the assembler (since `data.message` is None/unchanged).
- FIX VERIFIED (Turn 8, shadow file): in `SessionLifecycleManager.resume`'s `PENDING_PLAN` NON-communication branch, when `message` is supplied, parse the pending plan (`_parse_awaiting_plan`), seed `plan.metadata["user_request"] = message`, and call `orchestrator.execute(plan=plan, plan_path=plan_path, interactive=..., project_context=..., pipeline=...)` WITHOUT `message=`. The communication-turn route (`_consume_awaiting_reply`, Bug 57) and the no-message re-execute path are unchanged. Shadow MRE output: `{'interactive=False': True, 'interactive=True': True, 'no_message_reexecutes': True}` → `FIX VERIFIED` (rc=0), versus the RED baseline of `{'interactive=False': False, 'interactive=True': False, 'no_message_reexecutes': True}` (rc=1).
- RESOLVED (reading, Turn 13): the shipped fix must parse the pending plan WITH `plan_path` so `Plan.is_session`/`Plan.plan_path` survive. The parser stores `plan_path` on the `Plan` and derives `is_session` from it; because `execute(plan=plan, plan_path=...)` short-circuits `_resolve_plan`, a path-less parse would silently drop both fields in production (masked in the shadow MRE by a mock parser). No port/signature/DTO change is required — the correction is internal to the PENDING_PLAN branch.

## Solution

**Root cause.** `SessionLifecycleManager.resume`'s `PENDING_PLAN` NON-communication branch called `orchestrator.execute(plan_path=..., interactive=..., project_context=..., pipeline=...)` WITHOUT threading the injected `message`. This is the only dispatch site in the resume state machine that silently discards an injected `-m` reply (Bug 57 fixed only the COMMUNICATION-turn sub-branch via `_consume_awaiting_reply`). For a non-communication pending turn (a normal `plan.md` with no `report.md` and no `awaiting_reply` flag), `resume -m "<msg>"` re-executed the pending plan and the message vanished — no user-request section, no TUI seed.

**Fix (Shadow-Verified).** In that branch, when `message` is supplied: parse the pending plan WITH its `plan_path` (so `Plan.is_session`/`Plan.plan_path` survive — a path-less parse silently drops both because `execute(plan=...)` short-circuits `_resolve_plan`), seed `plan.metadata["user_request"] = message`, then call `orchestrator.execute(plan=plan, plan_path=plan_path, interactive=..., project_context=..., pipeline=...)` WITHOUT `message=`. Empirical proof: `spikes/debug/60-resume-m-pending-plan-mre.py` goes RED (`{interactive=False: False, interactive=True: False, no_message_reexecutes: True}`, rc=1) against the real code and GREEN (`{interactive=False: True, interactive=True: True, no_message_reexecutes: True}`, rc=0) against `spikes/debug/shadow_session_lifecycle_manager.py`.

**Why seed plan metadata rather than forward `message=`.** (1) The report assembler resolves `user_request = data.message or plan.metadata["user_request"]` (`execution_report_assembler.py:38`), so seeding satisfies the `-y` facet (the report renders the `## User Request` section). (2) `ExecutionOrchestrator.execute(message=...)` never reaches the interactive reviewer, so a forwarded `message` cannot seed the TUI; seeding `plan.metadata["user_request"]` DOES — the TUI `m` handler pre-loads its editor from it when no edit is buffered. (3) Passing `message=` would WIN in the assembler over `plan.metadata["user_request"]`, discarding a TUI harvest — breaking the required "an edit overrides the initial `-m`" behavior.

**Systemic prevention.** The defect class is "an injected `resume -m` reply is dropped on a `PENDING_PLAN` turn"; its two instances were the COMMUNICATION turn (fixed by Bug 57) and the NON-communication turn (this Case). The durable systemic fix — a single source of truth for the "interrupted-at-a-reply" state, set on BOTH stop paths, which would collapse the two-factor inference (`awaiting_reply` flag OR `is_communication_turn` shape) into one branch — is already logged as PROJECT.md Technical Debt and remains scheduled for Milestone 5. This Case's scope is the reported non-communication gap; the fix is confined to one file with zero consumer ripple.
